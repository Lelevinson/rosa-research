## Reproducible menu rule for a new deployment

1. Start with the deployment's actual registered ROS 2 tool inventory and the generic ROS log-inspection tools. Select a tool only if its implementation and allowed argument domain have been reviewed and certified as observational for that deployment. **Do not infer read-only behavior from a tool name, description, or JSON schema alone.** Separately enforce appropriate time/output bounds, target access and least privilege; preserve the runtime execution guard. Add the separate `final_answer` tool.
2. Applying the **selection classification** to the checked stock registry gives the 11 intended observational ROS 2 graph/topic/parameter/diagnostic/log-list tools and the separate `read_log` tool. Exclude `ros2_param_set` and unrestricted `ros2_service_call`; do not add unrelated calculation, ROS 1, or host-system tools just because they exist. The resulting names are exactly the existing 12: `ros2_node_list`, `ros2_topic_list`, `ros2_topic_echo`, `ros2_service_list`, `ros2_node_info`, `ros2_topic_info`, `ros2_param_list`, `ros2_param_get`, `ros2_service_info`, `ros2_doctor`, `roslog_list`, and `read_log`. This equality is a static source classification, **not proof that the current tools meet the deployment bounds**. For example, echo's tool timeout does not itself guarantee a process-level deadline, and log reads need output and privacy controls. Enforce and verify those separately before deployment; if a tool's allowed domain cannot be certified and bounded, omit or wrap it and report the resulting difference from C1.
3. If a task cannot be witnessed with the certified menu, identify the missing **capability**, not merely the failed reference path. An unrestricted service caller does not become safe because one requested service happens to be read-only. A deployment may separately authorize a narrowly constrained adapter or a verified service/type/argument allowlist, with explicit fallback and identical rights in every arm. Then rerun a model-free witness and record actual capabilities, costs and risks. The proposed rule does **not** include unrestricted `ros2_service_call`; it covers the six stale-value cases only if the unverified `ros2_param_get` alternative is subsequently checked. For Nav2, no coverage claim can yet be made.

This is a procedural safety/coverage policy, not proof that an automatically generated menu exactly matches C1 in every deployment. Counts describe these frozen pools only; no held-out data were used to revise method behavior.
