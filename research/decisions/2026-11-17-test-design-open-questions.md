# Test design questions for the team

2026-11-17. These are proposals for discussion, not authorization to run, change a frozen protocol, or select a claim. Keep evaluation pools custodian-controlled and report aggregate results only until the protocol permits disclosure.

1. **Models.** Proposed eligibility: a model runs locally, accepts the declared tool menu at the fixed context, and makes a structured tool call in a two-episode development check. Record exact model digest, Ollama version, settings, hardware and both outcomes; a check establishes interface viability, not task competence. Never select models by evaluation score. Predeclare family and version selection before the checks, and record every candidate and failure. Candidates for feasibility include Llama, Gemma, Granite and Ministral, subject to actual hardware and tool support. Current four pilot models represent three families, not four. How many new families can we afford, and what is the rule when a candidate fails the interface check?
2. **TurtleBot3 + Nav2.** Propose 24 cases as an initial planning target, with complexity and changing-state proportions frozen before construction; choose the final size against time and minimum event counts, not a convenient number. A custodian independent of method design should build and verify it, with another person checking oracle, resets, scoring and provenance. Existing simulated navigation smoke succeeded, but shutdown needed escalation and headless rendering accessed the GPU interface; it is not a held-out pool. Budget setup, environment repair, fixture resets, independent checks and storage as well as episodes. Who is available, and which machine can provide isolated GPU and ROS resources after Round 2?
3. **Comparators.** List arguments and the answer checker are dropped; do not silently restore either as the contribution. After Round 2 is scored, decide whether sweep and name rewrite merit further testing. A minimum matched comparison is fixed loop versus each retained add-on alone, plus their combination only if both are retained; preserve identical tools, prompts, model settings and scoring. Include stock ROSA and a defensible released baseline such as Forge when the question is whole-system comparison, with interface differences disclosed. Add a strong ordinary prompt/batching control for sweep and a simple exact unique-name baseline for rewrite; distinguish method effects from bundled loop differences. Freeze arms and costs before held-out use. Round 2 is still running: no result or promotion is assumed.
4. **Temperature.** Current development protocol uses 0.7. Retaining 0.7 preserves comparability; lower temperature could reduce sampling variation but changes the tested system. Should a small, separately identified development check compare 0.7 with a fixed lower value before freezing all arms? Do not choose using held-out scores. Equal seeds do not ensure identical random trajectories across systems.
5. **Rounds.** Propose one development decision after Round 2, at most one separately frozen repair/replication round if a concrete defect warrants it, then one untouched held-out evaluation after a claim and stopping rules are fixed. Further rounds need an explicit new decision and new held-out protection; report every previous result and failure. How many replications and independent environments are affordable?

## Planning time budget

Illustrative person-hours and elapsed compute; not measured forecasts or approved resource allocations. Do not add parallel person-hours to machine-hours as if they were the same resource. Re-estimate after a bounded development timing check.

| Activity | Person-hours | Machine elapsed | Decision / dependency |
|---|---:|---:|---|
| Select and check up to four model candidates | 2–4 | 1–3 h | Eight development episodes maximum, plus loading; record exclusions |
| Lab setup and matched check | 3–6 | 1–3 h | Access, model/environment identity and comparable behavior |
| Nav2 pool construction and independent verification | 16–32 | 8–24 h | Custodian and reviewer; setup failures may increase cost |
| Protocol, controls and scorer freeze | 4–8 | 0–1 h | Decide arms, uncertainty, stopping and invalid-episode rules |
| Evaluation planning example | 2–4 | 21–63 h | 76 existing cases × 4 models × 3 arms × 1 repetition = 912 episodes; 1–3 min each, plus 6–18 h setup/retries. Illustrative only; excludes new Nav2 pool and additional repetitions |
| Independent analysis and report | 8–16 | 1–3 h | Audit failures, all-episode costs and model/pool denominators |

The episode estimate extrapolates across heterogeneous tasks and models; pilot medians and tails vary materially. Measure actual throughput before scheduling. A 24-case Nav2 pool under the same example adds 288 episodes (4.8–14.4 h at 1–3 min) before setup, retries and simulation overhead. More seeds multiply the episode work. These numbers do not authorize runs or reserve hardware.
