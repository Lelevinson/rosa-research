## What is being tested

The answer rewrite in [`round2_harness.py`](../studies/build_round2_20261116/round2_harness.py) is shadow-only today. It rewrites name-like values and nested keys, never top-level keys, when a non-exact name is a whole-segment suffix of exactly one name from the task text or successful observed tool results; ambiguous or unseen names stay unchanged and are logged, not rejected. Apply **that exact rule** at final submission in the treatment, and keep the unmodified answer plus an event log. The control uses the same rule in shadow and submits the original. Both use C1 with sweep/gate/list/H2 off; the model's prompt, requests, tools and evidence do not change. The rewrite is post-model, so the live application can be paired **within the same episode**: score the original and the actual submitted rewrite on exactly the same trace. This tests the applied answer transformation, not an interaction with the model after feedback.

This is not pilot H2: H2 rewrites a failed tool argument and retries a tool. That prior study found one harmful repair out of 17, and apparent savings within run noise ([analysis](../studies/residual_failures_20261115/WASTE_BY_CAUSE.md)). **Dated denominator clarification, 2026-11-17:** Round 2 checked 296 answer objects in shadow, but rewrote only **2 answers**, both originally unsupported, representing one matched cell in the two arms. Both rewritten answers were scored supported. Thus the safety exposure is **2 rewritten answers**, not 296; for the specific supported→unsupported transition there were **0 originally supported rewritten answers**, so its denominator is **0**, not evidence that rewrite was safe on supported answers. The 296 is the screening denominator only ([report](../studies/build_round2_20261116/REPORT.md)). This is too little applied evidence. Freeze collision behavior before execution: if two nested keys would become the same key, **do not silently overwrite**. Existing code needs a documented test: if it can overwrite, the exact rule fails the preflight and applied use is blocked until a separate dated rule revision is authorized. Do not call a changed rule the identical round-2 rewrite.

## Dual scoring, frozen before this run

**Strict (primary):** unchanged scorer v2.0 and its complete source-support requirement, including exact requested name spelling and keys, evaluated on both original and submitted answer and identical evidence. A test-specific task/fixture adapter can translate these dev templates into the existing scorer's inputs but cannot alter v2's rules; freeze adapter and prove on positive and negative fixture examples that no missing/unsupported value can pass. If v2 cannot score a new task without changing its rules, that task is **BLOCKED**, not silently scored by a substitute. The v2 source hash is recorded in the [scorer decision](2026-11-15-scorer-v2.md).

**Lenient (secondary sensitivity):** a separate, frozen scorer applies the same completeness, evidence, value, type, timing, absence, and extra-key rules as strict; the only relaxation is a short relative suffix for a *name-bearing field or nested key* that resolves uniquely, by whole path segments and entity kind, against the independently verified full task-time graph. The resolved name must equal the required identity. Even where the task explicitly requests a full name, this secondary score asks whether the short answer identifies the right entity; it does **not** say the output met that full-name contract or is safe for a machine endpoint. If the graph is incomplete, there is more than one candidate, or an absolute full name is wrong, no leniency. No leniency to unrelated strings or wrong values. Keep original and transformed answers unmodified as evidence; the graph is only evaluator information and is never supplied to the model or repair. Freeze per-field eligibility and the test fixtures before model output. This is a new secondary metric, not a v2 change; never retroactively alter the held-out scorer or its interpretation.

Report four cells for **every planned episode**: strict original / strict applied and lenient original / lenient applied, with paired supported→supported, unsupported→supported, supported→unsupported and unsupported→unsupported counts. Include no-answer and aborts, and denominator 64; separately report emitted answers, rewritten episodes, rewritten fields/keys, eligible shorthand, ambiguous/unseen/collision cases, wrong-identity rewrites and task/model slices. For safety, report harmful rewrites / **answers actually rewritten**, and supported→unsupported / **originally supported answers actually rewritten**; if either denominator is zero, mark that rate unavailable. Do not use all checked answers as the safety denominator. Cite exact trace and independently audit every changed answer, every strict improvement and every support loss; adjudicate against fixture truth and evidence, not the rewriter's ledger. Report unchanged exact full-name answers, not just improvements. A strict improvement that is already lenient-supported is formatting/identity presentation benefit; an improvement on both scorers is stronger evidence of answer-level change. No cost claim from a post-submission rewrite; measure extra CPU/time and report model/native requests are the same within the paired trace.

## Decision bars written now

**Safety FAIL:** even one originally strict-supported answer becomes unsupported, a wrong-identity rewrite, or a key collision/overwrite; one is enough because the feature changes a submitted answer without user review. **Eligible for consideration:** zero such harms among the actually rewritten answers, at least 8 episodes with an actual rewrite across at least 2 models and 2 distinct task templates, and at least 2 strict unsupported→supported episodes with independently verified correct identity and complete evidence. Eight events give more than the prior two changes in one cell; two models/templates prevent a single repeated trajectory from determining the decision. Two improvements require repeated benefit but are not statistical power or broad safety proof. If fewer events/improvements occur without a safety failure, **INCONCLUSIVE / NOT SHOWN**, not safe or useless. Report a stricter verdict if the adapter or evaluator cannot be frozen or support checked. Apply the same bar before reading results; any later revision is a new dated proposal.

## Why a full name can matter

In a multi-robot or namespaced ROS deployment, `/robot_a/camera` and `/robot_b/camera` may share the short name `camera`. A human can sometimes infer the intended entity from context, but an API call, log correlation, automated monitor, or handoff between nodes may need the namespace to identify the target. Relative names also resolve according to context; the [ROS 2 naming design](https://design.ros2.org/articles/topic_and_service_names.html) distinguishes relative and fully qualified topic/service names. For a human-facing answer where one entity is truly unambiguous and the task permits shorthand, a short name can still communicate the right identity; a strict exact-name score and a context-lenient score therefore answer different questions. Neither an apparently unique observed suffix nor this limited development test guarantees uniqueness in a changing or partially observed graph.
