## Objective and design

Assess read-only information gathering about a simulated robot with a running navigation stack: can an agent obtain current, supported facts and report them correctly at a reasonable cost? This pool is one simulated configuration, not a representative sample of all robots, environments, Nav2 deployments or operators. Distinguish simulator truth, ROS graph observations and model outputs. Do not use evaluation results to adjust the pool or methods.

Propose **24 tasks**, six categories with four tasks each. This provides some variety within each category and matches the size of the earlier simulator pool while keeping independent verification manageable. It is a coverage choice, not a power calculation; four per category cannot support precise category-level estimates. Choose independently from an operator-oriented inventory before examining method behavior. Within each category use distinct information needs and, where possible, different components. Avoid treating repeated wording or shared runtime state as independent environments. If a category or complexity quota cannot be met naturally and verified, stop and ask the owner to approve a separately recorded revision; never fabricate complexity.

| Category | Count | Operator information need |
|---|---:|---|
| Service ownership and availability | 4 | Identify the responsible component and whether its interface is available. |
| Configuration across components | 4 | Check or compare relevant runtime configuration. |
| Topic inputs and participants | 4 | Establish what feeds or consumes an observed interface. |
| Lifecycle and readiness | 4 | Determine component states and their bearing on operational readiness. |
| Navigation state and localization | 4 | Establish the current robot or navigation state with explicit timing. |
| Cross-component diagnosis | 4 | Relate multiple independently observable facts to a narrowly specified operational condition. |

### Pre-build complexity allocation

Freeze this proposed mix **before drafting or selecting individual tasks**: 4 tasks requiring one lookup, 8 requiring two, 8 requiring three, and 4 requiring four or more. Assign a provisional category and complexity stratum before wording each case; freeze the final assignments before model exposure. A lookup is one original ROSA read invocation on one entity with its arguments known at invocation; a list argument containing multiple entities counts one lookup per entity. Count a successful catalogue read once, but each subsequent targeted entity read separately; final answer, setup and oracle reads are not agent lookups. Record native subprocess attempts separately, including failures. Multiple independent lookups can occur in one model request: lookup count is not model calls, sequential depth or an unrestricted minimum. Catalogues and other legitimate broad reads may change the cheapest route. Verify that each assigned complexity is a justified reference under an explicit targeted-read rule, and record valid shortcuts and costs; do not forbid ordinary enumeration merely to meet a quota. Freeze any support requirement independently of the reference route and do not require a particular route if equivalent evidence is valid.

## Step 1 — later, model-free tool-output census

After explicit authorization and only when resources are free, inspect the actual installed ROSA registry and the real, isolated navigation stack. Run a bounded census before constructing tasks, never a model. Pin the stack, tool source and configuration; establish readiness, record a snapshot of all discovered nodes, topics and services, and preserve discovery time and any changes. Use one entity per call for comparable size measurements, then optionally measure bulk calls separately. A read tool applies only to compatible inputs; do not pass every entity type to every tool indiscriminately:

- Call node, topic and service list tools globally; run node-info and parameter-list on every discovered node, topic-info and one bounded echo on every discovered topic, and service-info on every discovered service.
- For every parameter returned by each successful node parameter-list, attempt parameter-get, subject to the cap and timeout below; explicitly report unattempted parameters if the cap is reached. A topic echo uses one message with returned output enabled and a per-call deadline, including a process-level deadline because a tool argument alone may not bound a stalled subprocess. Record silent, unsupported or oversized topics as outcomes; do not repeatedly sample or retain uncontrolled payloads without limits.
- A generic service-call tool is **not inherently read-only**. Do not call every service. After inspecting each discovered service type, invoke only explicitly allowlisted, demonstrably read-only introspection services with valid requests; mark every other service as not invoked and why. No lifecycle transitions, navigation goals, parameter writes or other mutations during the census. Lifecycle answers may be usable only if an allowlisted read-only query and the eventual agent tool menu support them; otherwise the category is blocked pending a separately approved design. Run global diagnostics and log metadata reads only if in the intended registry and safe for the isolated environment; do not collect secret-bearing log contents.
- For every attempt record tool, input class, success/error/timeout, elapsed time, output bytes, item counts, native subprocess attempts and failures; also record serialized token counts using the proposed model tokenizer if available, otherwise label characters/4 as an estimate. Preserve raw receipts in custodian-only evidence, and publish only aggregate counts and size distributions. Mark discovery churn, truncation, unsupported types and failed reads explicitly; never treat failure as absence.

Proposed safety and resource bounds to approve before the census: one isolated stack and domain, maximum 500 tool invocations and 15 minutes of census execution after readiness, 10 seconds per tool subprocess, and 1 MiB captured per individual output with an explicit truncation marker. Record attempts cut short by a cap; stop on unexpected mutation, unsafe output, discovery instability, uncontrolled resource use, cleanup failure or stack fault. Output handling and outer deadlines must be implemented and checked before execution. These bounds may prevent a complete inventory; in that case report it as incomplete and request a revised bounded plan. Measure startup, memory and GPU use separately. A larger population or command needing more time requires an owner-approved amendment, not silent expansion.

## Ground truth, support and temporal contract

After the census and only with separately authorized pool construction, the custodian creates cases from the operator categories and frozen mix. A model-free, independent oracle uses ROS APIs or separately instrumented direct observations, with a second independent check where feasible; do not assume that the same tool output independently validates itself. Verify actual discovery, identity, types, values and runtime lifecycle state, not configuration files alone. Capture timestamped before/after snapshots, reset state, environment and source hashes. An independent reviewer checks all 24 cases for operator relevance, supported answerability, ambiguity, expected results, observed evidence, lookup accounting and shortcut possibilities without using a model. Preserve failed checks and all revisions; freeze tasks, oracle, scoring, acceptance and manifests before model use. A material mismatch blocks freeze. Give models only the authorized task and ordinary tools, never oracle or scoring metadata.

For every case define required evidence by claim and accepted equivalent observations; check actual successful observations and values, not attempted calls. Verify exact answer and evidence support separately with a frozen scorer, including stale, missing, extra and ambiguous information; failed or timed-out episodes stay in denominators under rules fixed before evaluation. Use a held-out scorer review and tests with synthetic non-held-out examples; avoid tuning after exposure. Common ordinary tools and capabilities must be available to all arms. Report supported completion first, then requests, native attempts/failures, tokens, result sizes, wall time, reset/oracle costs and invalid episodes, by arm and pool. Treat reference lookup counts as conditional comparisons rather than universal lower bounds.

For changing values, predeclare the time and frame, source, precision or tolerance and what the answer is required to mean. Prefer a stable observation window or a bounded predicate with explicit margins; record start/end and verify stability independently. For genuinely moving values, use a time-stamped observation and a scoring contract aligned to that timestamp, or an independently captured answer-time truth with a predeclared freshness bound; do not compare asynchronously sampled exact floating-point values. If the truth cannot be verified reliably within the bound, classify the episode as infrastructure-invalid under the frozen rules and preserve its evidence. Separate an infrastructure-invalid episode from an agent timeout or unsupported answer; report all denominators and missed observations. Decide reset, timing and any scripted external change before freezing, and apply identically to every arm. Census itself does not command motion.

## Cost and stopping estimates

These are planning allowances, **not measurements**. A first authorized model-free timing pilot must measure them before any evaluation budget is committed. Reset and readiness may dominate inference; no shared setup should be omitted from total cost.

| Per episode component | Provisional elapsed allowance | Accounting |
|---|---:|---|
| Reset, readiness and independent before check | 1–3 min | Record setup/fixture attempts and failures. |
| Agent interaction | 1–3 min typical planning assumption; 15 min hard timeout proposed | Count all model calls, token usage, tool calls and native attempts; actual tails may differ. |
| After oracle, validity check and cleanup | 0.5–2 min | Include actor and oracle cost; identify amortized shared startup separately. |
| **Total** | **2.5–8 min typical allowance** | Up to 20 min planned cap including 15 min agent timeout and 5 min for setup/checks; abort safely if exceeded. |

At 24 cases, one model, one arm and one repetition this implies 60–192 minutes of episode time, excluding shared startup and contingency. Four models × three arms × one repetition = 288 episodes, or 12–38.4 hours under the allowance, before startup, cleanup recovery, repetitions or invalid reruns. These are scheduling arithmetic, not predicted completion times. Freeze a retry/invalid-episode policy before running; do not discard failures. Measure cost of the census and verification separately.
