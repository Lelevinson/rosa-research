# Primary-source mechanism review: native read execution

Reviewed 2026-11-11. This is a source-based analysis, not an experimental result. Remote `master`/`jazzy` links are moving branches; local source identities and experimental freezes must be recorded separately. The ROS documentation HTML endpoint denied access, so official repository source was inspected instead.

## Closest adaptive concurrency controls

**Netflix AIMD is a directly applicable ordinary control.** Its implementation decreases `L` to integer `L*backoffRatio` when a request drops or RTT exceeds a timeout. Otherwise it adds one when `2*inflight >= L`, then clamps to `[minLimit,maxLimit]`. Defaults are initial/minimum 20, maximum 200, backoff 0.9 and timeout five seconds. A small ROS batch requires explicit smaller initial/minimum/maximum values, shared with the candidate. Call this an AIMD port with disclosed parameter changes; it is not a new method. Update from completed requests, with request-admission concurrency captured consistently. [Official AIMD implementation](https://raw.githubusercontent.com/Netflix/concurrency-limits/master/concurrency-limits-core/src/main/java/com/netflix/concurrency/limits/limit/AIMDLimit.java).

**Netflix Gradient2 is a stronger delay-sensitive challenger if latency inflation is the candidate signal.** The code computes `g=clamp(tolerance*longRTT/currentRTT,0.5,1)`, `target=L*g+queueSize`, and smooths toward that target. It declines growth for application-limited samples. Defaults include tolerance 1.5, smoothing 0.2, queue allowance four and long window 600. The implementation also reduces a badly inflated long RTT estimate when `longRTT/currentRTT>2`. Preserve these details or label an implementation “Gradient2-inspired,” not an exact reproduction. A short finite batch may not provide enough feedback to learn useful settings; this is an applicability question to measure. [Official Gradient2 implementation](https://raw.githubusercontent.com/Netflix/concurrency-limits/master/concurrency-limits-core/src/main/java/com/netflix/concurrency/limits/limit/Gradient2Limit.java).

The long RTT estimator initially averages ten samples, then uses exponential averaging with factor `2/(window+1)`. That initialization matters in a short experiment. [Official averaging implementation](https://raw.githubusercontent.com/Netflix/concurrency-limits/master/concurrency-limits-core/src/main/java/com/netflix/concurrency/limits/limit/measurement/ExpAvgMeasurement.java).

Netflix's optional window wrapper defaults to one-second windows, at least ten samples and a 100-microsecond RTT threshold. It forwards aggregate RTT, maximum inflight and drop information only from sufficiently populated windows. A per-request port and a windowed port are distinct baseline configurations. [Official window implementation](https://raw.githubusercontent.com/Netflix/concurrency-limits/master/concurrency-limits-core/src/main/java/com/netflix/concurrency/limits/limit/WindowedLimit.java).

For complete-answer batch work, queueing unadmitted reads is the appropriate adaptation. Silently rejecting excess reads would weaken answer coverage. Netflix itself distinguishes backpressure for batch applications from fast failure for interactive clients. [Official project rationale](https://raw.githubusercontent.com/Netflix/concurrency-limits/master/README.md).

## Existing parallel agent execution

LLMCompiler already separates a model-generated function plan, task fetching and parallel execution. Its published speedups are task-specific and are not expected ROSA gains. Scheduling an already-bound list avoids requiring a generated dependency plan, but that difference alone is an integration boundary, not a novel scheduling algorithm. A new claim needs a measured advantage in action selection over ordinary concurrency, with identical request obligations. [Original ICML 2024 paper](https://proceedings.mlr.press/v235/kim24y.html).

## Persistent transport and semantic constraints

The official Jazzy `AsyncParameterClient` builds clients once and `get_parameters(names)` calls `call_async` with a list. However, its constructor creates six read/write service clients and `wait_for_services` checks all six, including write services. A strictly read-only harness should create only the needed read client, or explicitly avoid using all-service readiness as a read-availability condition. Merely constructing a write client does not issue a write, but unnecessary endpoints and readiness conditions distort setup costs. [Official Jazzy parameter client](https://raw.githubusercontent.com/ros2/rclpy/jazzy/rclpy/rclpy/parameter_client.py).

`GetParameters` explicitly returns values with the same length/order as request names and marks an unset value with `PARAMETER_NOT_SET`. Thus grouped native parameter retrieval is already supported and belongs in a fair baseline when its semantics match the task. [Official service definition](https://raw.githubusercontent.com/ros2/rcl_interfaces/jazzy/rcl_interfaces/srv/GetParameters.srv).

The generic client supports multiple pending asynchronous requests indexed by sequence number; it locks request submission and returns a future. `call` blocks and warns against use within callbacks because deadlock or timeout can result. This supports a reusable client as an ordinary transport alternative; it does not prove server-side overlap. [Official Jazzy client implementation](https://raw.githubusercontent.com/ros2/rclpy/jazzy/rclpy/rclpy/client.py).

The default callback group is mutually exclusive. Reentrant groups and separate groups permit concurrency; the executor and server callback arrangement still constrain actual execution. Measure client overlap and server overlap separately rather than treating futures as evidence of parallel service processing. [Official Jazzy callback-group guide source](https://raw.githubusercontent.com/ros2/ros2_documentation/jazzy/source/How-To-Guides/Using-callback-groups.rst).

Graph inspection is different from remote parameter service calls. `ros2 node info` asks graph APIs for subscriber, publisher, service and action information; `ros2 topic info --verbose` retrieves types, counts and endpoint metadata; `ros2 service type` looks up the graph service-name/type list. Persistent observation can reduce transport/interpreter setup, but must preserve all requested categories, errors and namespaces. [Node-info source](https://raw.githubusercontent.com/ros2/ros2cli/jazzy/ros2node/ros2node/verb/info.py), [topic-info source](https://raw.githubusercontent.com/ros2/ros2cli/jazzy/ros2topic/ros2topic/verb/info.py), [service-type source](https://raw.githubusercontent.com/ros2/ros2cli/jazzy/ros2service/ros2service/verb/type.py).

CLI subprocess creation is **not** evidence of fresh DDS discovery per read: Jazzy `NodeStrategy` reuses a daemon when available and delegates supported methods to it, otherwise using a direct node. Compare cold and warm setup explicitly. A persistent direct client and an already-warm CLI daemon may observe graph changes at different times. [Official strategy source](https://raw.githubusercontent.com/ros2/ros2cli/jazzy/ros2cli/ros2cli/node/strategy.py).

## Decision and actionable comparison

1. Hold request list, per-entity result obligations, permissions, timeout and native operation count fixed. Compare serial, bounded fixed widths (at least two and four), and AIMD with an equal width ceiling. Include an execute-all-ready bound where safe and within the same resource cap.
2. If the candidate reacts to RTT trends, include Gradient2 or explicitly limit the claim to comparison with AIMD. Give controllers identical passive observations, warmup opportunities and calibration charges. Preserve state scope across batches explicitly.
3. Compare an always-persistent read observer separately from width policies. It changes transport and setup lifetime; do not attribute those gains to adaptive width. Charge initialization, discovery waits, shutdown and every read/error.
4. Test stable mappings and missing entities before latency. Graph metadata is not an atomic snapshot; asynchronous clients do not manufacture stronger consistency.
5. A candidate using only RTT, inflight and drop feedback currently has no demonstrated new mechanism relative to these controls. A new policy requires a distinct observable signal/action rule and held-out cost benefit. Otherwise retain measured parallel/persistent transport results as ordinary systems engineering and a bounded negative algorithm study.
