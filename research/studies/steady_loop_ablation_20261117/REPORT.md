## 3. Audit of discordant cells and exposures, and the frozen reading (measured, then interpretation)
Rule recalled: important benefit needs FULL >= 3 more supported **and** at least two FULL-only disagreements with a trace-supported mechanism chain tied to the component; harm is symmetric; a blocked write is a safety finding regardless; a smaller net gap, absent mechanism or contradictory outcomes = INCONCLUSIVE / NO CLEAR EFFECT. Efficiency is flagged only for a change of >= 10% in requests or tokens with at least two trace-supported exposure cases explaining the direction and no correctness harm.

**Minus soft errors: net +2 (3 FULL-only, 1 removal-only) -> below the 3-cell threshold: NO CLEAR EFFECT (by the rule).** Exposure (measured): 5 episodes ended by error (5 of 40): 3 gpt-oss `blacklist` argument errors at request 1 (`e1h_abs_1`, `e1h_abs_2`, `v2`: the call `blacklist: ""` where the schema wants an array; FULL got the same invalid call in `e1h_abs_2`, was told, retried and answered correctly, 3 requests), and 2 regex errors (`pattern: "*cedar*"`) in `v2` cells where FULL also failed. So the mechanism (soft errors let gpt-oss recover) is trace-supported in at least 1 and plausibly 3 cells, but the net is 2 and the third supported-FULL cell has a different request-1 call. The removal-only cell is the hook defect (not an effect of the component). Efficiency: -1.9% requests, -3.8% tokens: below 10%, and the episodes are cheaper only because they ended.

**Minus pre-check: net -1 (0 FULL-only, 1 removal-only): NO CLEAR EFFECT; no harm.** Exposure (measured): 5 stock validation errors returned as text, 0 pydantic coercions, 4 tool exceptions; FULL had 1 pre-check rejection in the whole arm. With so little exposure this cannot show the pre-check is unnecessary: it was almost never used. Efficiency +4.3% requests, +5.7% tokens: below 10%.

**Minus short menu: net +6 (7 FULL-only, 1 removal-only) -> number above the threshold, but no trace-supported mechanism chain: INCONCLUSIVE for support.** The 7 FULL-only cells (`e1h_abs_1` bonsai and gpt-oss, `e1h_chg_1` lfm3, `e1h_chg_2` bonsai, `h4` bonsai and gpt-oss, `p3` bonsai) diverge from FULL at request 1 in 6 and at request 3 in 1; none used a tool outside the C1 menu (extra-tool use occurred in one non-discordant episode); 3 had a pre-check rejection from gpt-oss' `blacklist` or a stray argument. Plausible, not established: a larger schema list changes the first sample. **Efficiency flag: tokens +155%, explained** by a measured structural cause: the 35 extra schemas add **+3,338 (lfm3), +3,666 (qwen3.5), +2,029 (gpt-oss), +3,666 (bonsai) tokens to every request** (request-1 input differences on identical cells; 13 -> 48 offered tools verified in every trace). Requests +18.5% (bonsai 64 -> 88) are not attributed. **Safety finding (measured):** in `v2`, bonsai called `ros2_service_call` on `/plant32/cedar_reset` 4 times (the service is named in the task); the unchanged observation-only guard blocked all 4, none reached ROS. With a different guard a reset service would have been called.

**Minus finish tool: net +7 (8 FULL-only, 1 removal-only) -> number above the threshold, no established mechanism chain: INCONCLUSIVE for support; requests +11.8% flagged but not attributable.** All 40 answers were free text (scorer v2.0 last-JSON rule). Of the 8 FULL-only cells: 1 is the hook defect (`e1h_chg_1` gpt-oss), 1 a backend XML tool-call error (`e1h_chg_2` bonsai), 3 are the absent-node tasks (`e1h_abs_1` x2, `e1h_abs_2`) where the model resolved the short name to an existing node and answered with its details, 3 ended with a text turn built from an incomplete read chain (`p3` bonsai and lfm3, `v2` qwen: no node in the answer). Sampling diverges at request 1 (4 cells) or 2 (4 cells), so "no finish tool" cannot be separated from sampling by the trace. **Interpretation (hypothesis, not tested):** without the "call final_answer when you have the answer" cue models stop with text earlier or later, and the free-text step loses cases where the finish tool's required object forces completion; the consistent sign in all four models (-3 / -1 / -1 / -2) is the only support. The tool and its prompt line are bundled by protocol, so schema alone is not isolated.

## 4. Map of the fresh FULL arm (the owner's request; 40 episodes; definitions fixed before the numbers: `FULL_ARM_MAP_DEFINITIONS.md`)
### (a) Input tokens per request (measured, reported prompt tokens; the provider's cache is not visible)
Total input of the 40 FULL episodes 721,646 tokens over 211 requests. **Fixed content re-sent every request (system prompt + tool schemas + task) 376,724 (52%); old history re-sent 269,137 (37%); new content 75,785 (10.5%).** Output 54,968 is separate. New content per request averages about 230 to 590 tokens (one request of 2,548 at step 13: a long `read_log`/list result); history grows by roughly 300 to 700 tokens per step. By model: for qwen3.5 and gpt-oss (short episodes: 3.8 and 4.7 requests) the fixed part is 76% / 74% of input; for lfm3 and bonsai (6.2 and 6.4 requests, with long failures) history is 48% / 43% and fixed 39% / 49%. Estimated split of the fixed part (characters-proportional, an ESTIMATE; the exact differences from the other arms agree in size: 35 extra schemas = 2,029 to 3,666 tokens, i.e. about 58 to 105 tokens per schema; 13 schemas = about 1,400 per request for qwen3.5): system prompt about 93k tokens (13% of all input), tool schemas about 269k (37%), task text about 14k (2%). Removing the finish tool and its prompt line saves only 87 to 125 tokens per request (exact). The growth shown is for episodes that reach each step, so later steps are the long, mostly failing episodes (survivor effect).
**Interpretation:** about 90% of all input is text the model already had (fixed or history); what each step adds is about a tenth. Per-request cost is therefore driven by the number of requests times the fixed part (schemas about 1,400 tokens) and, in long failing episodes, by history.

### (c) Unsupported FULL cells (4 of 40; measured = scorer v2.0 issue, interpretation = cause from reading the trace)
- **lfm3 v2 (16 requests, floor 3):** node `/plant32/cedar` != `/plant32/wharf`. Cause: name guessed from the service name; 6 `node_info` lookups of invented node names (`cedar_reset`, `cedar`, `cedar-reset`, `cedar_node`, `knoll`, `Cedar`) all returned not-found, 2 regex errors from `*cedar*`, the 19-node list was read at request 4 but only 2 of its nodes were ever inspected; final answer is a name the model had already seen to be absent.
- **gpt-oss e1h_chg_2 (4 requests, floor 3):** `final_mode` idle != run. Cause: **validity defect, not a model error**: it wrote `e1h/willow` without the leading slash, the fixture hook did not fire, so the parameter never changed (the same cell is supported in all four removal arms, which used `/e1h/willow`).
- **bonsai v2 (17 requests, floor 3):** node `/plant32/cedar` != `/plant32/wharf`. Cause: same as lfm3, with 3 glob-pattern exceptions and `roslog_list` as an off-path search; it verified at request 8 that `/plant32/cedar` does not exist and still submitted it.
- **bonsai e1h_abs_2 (2 requests, floor 2):** the answer is right (`running: false`) but the absence is "not shown": it asked about `alder/pewter` (no leading slash), so the not-found result does not prove that `/alder/pewter` is absent; correct but unsupported by evidence (answered on an invalid check).
Three of the four trace to a name problem (guessed name, or wrong name form); one is the hook defect.

## 5. Interpretation, in order of strength, and limits
1. **Measured and large:** the 48-tool menu costs 2.55x the tokens (66,065 vs 21,573 tokens per supported answer) and was never needed in these cells (extra tools used in 1 episode); it also advertised write tools that models tried to use. Keep the short menu on cost and safety grounds even if the 6-cell loss is noise.
2. **Measured, mechanism unproven:** the finish tool + prompt line is the component whose removal lost the most (7 cells, all four models, 3 to 7 depending on the control used). It cannot be split from its prompt line here.
3. **Not shown:** soft errors (net 2, 5 episodes ended by error, mostly gpt-oss `blacklist`) and the pre-check (almost no exposure). "No clear effect" must not be read as "unnecessary".
4. Where the requests go (section 4b) points at serial reads of sibling entities and name guessing, not at error handling.
Limits: one seed and 40 cells per arm; arms diverge from request 1 so pairs are not matched trajectories; the control's own range on these cells is about 4; one backend tool-call parse error and two hook defects sit inside the counts; development tasks only; nothing here is a significance or novelty claim. The fairness test's batching count (`fairness_errors_as_text_20261117/BATCHING_EXPLORATORY.md`) is exploratory and separate.
