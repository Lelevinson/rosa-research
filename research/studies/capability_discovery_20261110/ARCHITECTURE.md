# ROSA tool architecture inspection

Inspected local commit `94af17866cb82f3ea3f09422ef5cbb99b14cc89c` on 2026-11-10. This is a source inspection; it does not certify the semantics of registered tools. Installed dependencies inspected: LangChain 0.3.30, langchain-core 0.3.86, Pydantic 2.14.1.

## Registration and metadata

`ROSATools` loads calculation, log, system, and the selected ROS-version module. It scans public module attributes and accepts objects with `name` and `func`. `add_tools()` and `add_packages()` use the same append path. There is no registration-time capability ontology, read-only contract, semantic equivalence declaration, or duplicate-name check. `get_tools()` returns the underlying mutable list. These are concrete extension points for inventorying newly registered tools, although changing the registry after an existing agent has bound its tool menu does not itself rebind the model. Sources: [registry](../../../src/rosa/tools/__init__.py), lines 65–139; [ROSA construction](../../../src/rosa/rosa.py), lines 278–291.

When configured, blacklist injection wraps applicable `func` objects and changes their signature defaults. This is execution configuration that a relation cache must account for; the displayed input schema alone is not an identity of behavior. Source: [blacklist wrapper](../../../src/rosa/tools/__init__.py), lines 23–60, 94–99.

The ordinary `@tool` objects expose names, descriptions, `args_schema`, `tool_call_schema`, callable references, metadata/tags, and response-format configuration. The installed `StructuredTool.from_function()` infers **input** schema from the function signature and takes the description from its docstring by default. Input types, required fields, defaults, and supplied constraints are therefore automatically available. Its descriptions are textual assertions, not machine-checked semantic contracts. Existing ROSA tools generally do not attach semantic metadata or read-only declarations. Sources: [installed StructuredTool](../../../.venv/lib/python3.12/site-packages/langchain_core/tools/structured.py), lines 129–247; [installed BaseTool](../../../.venv/lib/python3.12/site-packages/langchain_core/tools/base.py), lines 396–499, 530–601.

Input schemas with the same structure are insufficient evidence of shared capability. For example, node/topic/service listing tools share optional `pattern` and `blacklist` arguments, but enumerate different entity classes. The mean, median, variance, and product functions also share input types while computing different quantities. Sources: [ROS 2 lists](../../../src/rosa/tools/ros2.py), lines 91–170; [calculation tools](../../../src/rosa/tools/calculation.py), lines 24–60.

## Outputs and observable evidence

The installed `BaseTool` is a `RunnableSerializable[..., Any]`. Its inherited `get_output_schema()` therefore provides a generic output schema for normal `StructuredTool` objects, rather than a schema inferred from the function return annotation. Underlying callable annotations remain inspectable, but ordinary ROS tools mostly annotate only `dict`; this does not describe fields, entity identity, units, freshness, or error alternatives. There is input validation, but ordinary `StructuredTool._run()` directly returns the callable result without return-annotation validation. Sources: [BaseTool](../../../.venv/lib/python3.12/site-packages/langchain_core/tools/base.py), lines 396, 835–875; [StructuredTool execution](../../../.venv/lib/python3.12/site-packages/langchain_core/tools/structured.py), lines 70–94; [Runnable output schemas](../../../.venv/lib/python3.12/site-packages/langchain_core/runnables/base.py), lines 444–480.

Concrete ROS 2 outputs are mixed. Lists return dictionaries containing lists. Node/topic/service info returns dictionaries keyed by requested entity, with CLI output strings or nested error dictionaries. Parameter-get returns `{param_name: CLI_output}`. Service-call returns a CLI response string under `response`. These are observations, not typed semantic propositions. List-helper failures can be embedded as list entries rather than a uniform error envelope. Source: [ROS 2 tool implementations](../../../src/rosa/tools/ros2.py), lines 25–88, 91–354.

`ros2_topic_echo` prints each received CLI string. With its default `return_echoes=False`, it returns only `{"success": True}`; the message payload is available in the returned observation only when explicitly requested. A discovery mechanism must not treat dispatch success, printed stdout, or the generic return annotation as evidence of payload fields. Source: [echo implementation](../../../src/rosa/tools/ros2.py), lines 115–156.

## Dispatch and safety boundary

ROSA builds a tool-calling agent from the registry and passes the same tool list into `AgentExecutor`. Installed LangChain binds the tools to the model, parses model tool actions, builds a name→tool lookup, and invokes the selected tool's `run()`/`arun()`. The asynchronous executor already gathers multiple tool actions concurrently. Sources: [ROSA agent/executor](../../../src/rosa/rosa.py), lines 256–276; [tool-calling agent](../../../.venv/lib/python3.12/site-packages/langchain/agents/tool_calling_agent/base.py), lines 97–112; [AgentExecutor](../../../.venv/lib/python3.12/site-packages/langchain/agents/agent.py), lines 1413–1446, 1543–1596, 1610.

ROSA's stream forwards `on_tool_start` input and `on_tool_end` output events. These are a possible passive observation hook for an opt-in research monitor; the current prototype need not alter dispatch. Source: [ROSA streaming](../../../src/rosa/rosa.py), lines 211–231.

The ROS 2 command wrapper checks only the top-level CLI family and executes command strings using `subprocess.check_output(..., shell=True)`. The registry includes parameter mutation and arbitrary service invocation, along with local debugging/verbosity state changes. Descriptions and signatures cannot establish that calling a newly registered tool is safe. Sources: [command wrapper and mutators](../../../src/rosa/tools/ros2.py), lines 25–48, 289–342; [system tools](../../../src/rosa/tools/system.py), lines 21–59. Consequently an adapter-free discovery prototype should inspect metadata and consume observations from already authorized read-only calls, or use explicitly controlled read-only fixtures. It should not autonomously probe the full registry or infer read-only status from names.

## Implication for capability discovery

Automatically available evidence supports schema compatibility checks, textual candidate proposals, observed output shapes, and falsification by conflicting runtime results. It does not supply semantic equivalence, entity alignment across renamed parameters, representation conversions, stable state identifiers, temporal validity, or permissions. A defensible mechanism must retain these gaps explicitly and preserve ordinary calls when they remain unresolved. Matching observations on finitely many inputs is bounded empirical support, including for newly added tools; it is not a general substitution theorem.
