# LISTVAL live development test: protocol (frozen 2026-11-20 before the smoke and before any measurement episode)

Authorised by the owner's message of 2026-11-20 (build with the switch default off; 288-episode run on the **laptop only**; freeze first, smoke first, stop after the report, ntfy). Source prompt: `Claude outputs/2026-11-20_CC_LISTVAL_LIVE.md`. **Label: live development test of one candidate (list results carry values). Development tasks only; nothing here is a held-out result and no claim about a final method follows from it.** No lab machine, no exam-queue spec change (a new spec and two new `LV-` lines in `exam_queue/systems.py` were added), no production default change (the switch is off unless the LISTVAL arm turns it on).

## 0. Preflight record (AGENTS.md; context 12.2 and 14.2)
- **Observed opportunity and evidence:** loss map (`loss_map_20261120/REPORT.md`): 111 successful `param_list` calls in 288 episodes, 107 followed by a `param_get` of the same node, the parameter name already known in all 107; offline sizing (`idea_search_20261120/claude_lane/REPORT.md`, candidate 3): saved-max 95 requests (5.7% of 1,655), added tokens 1,873 vs 334,440 (estimates), PASS on its frozen bars. Those numbers are upper bounds under the assumption that models use the inline values.
- **Candidate vs control action difference:** FULL returns parameter names only and the model must call `param_get`; LISTVAL returns `name: value` in the same call (values read at list time). Visible difference in a trace: a `param_get` that FULL makes after a list and LISTVAL does not.
- **Closest prior mechanisms and negative evidence:** the list sweep (`decisions/2026-11-17-list-sweep-whole-cost.md`: first-fire bars passed live, whole-episode tokens -1.4%, native operations +7.8%, no overall benefit demonstrated) and the finish-split / canonical-rendering live runs (class B). Whether LISTVAL is the same mechanism as any of them is not claimed here.
- **Fair evaluation and costs:** both arms in the same fixture session, adjacent, arm order alternated per cell, same seeds, models, settings and scorer; costs counted: model requests, input and output tokens, **native operations** (LISTVAL adds one native read per parameter of every inline list; expected to rise), wall time. The strongest ordinary control for "the model can skip the list" (a prompt change) is **not** tested; this test only asks whether the tool-output change alone changes behaviour.
- **Smallest decision-changing action and stop rule:** one 288-episode run, one report, no repeat, no tuning. The decision it can change: whether list values enter the component list at the Saturday 21 November freeze.

## 1. Build (committed before the freeze: `listval_arm.py`, `tests/`)
Executor option `inline_param_values`, default **False**. When True, a successful `ros2_param_list` with a `node_name` returns `name: value` per parameter, values read at list time through `rosa.tools.ros2.ros2_param_get` (same read-only path; each read is a counted native operation), if the JSON text of the rendered result is <= 2,000 characters; otherwise the original result. A value that cannot be read is shown as `<unreadable>` (never dropped). Nothing is cached; `param_get` stays live. Calls without `node_name`, failed calls and other tools are untouched. Switch off returns the original result object. Tool descriptions are the same in both arms (the model is not told). 11 unit tests (rendering, cap fallback and boundary, failed and raising reads, odd shapes, switch off identical, switch on only for `param_list` with a node). `listval_arm.py::ListValArm` subclasses the thinking study's `ThinkArm` in its FULL variant, so FULL here is that arm unchanged.

## 2. Design
- **Arms:** `FULL` (switch off) and `LISTVAL` (switch on), through the queue systems `LV-FULL` and `LV-LISTVAL` (`exam_queue/systems.py`), runner `run_listval.py`. Loss-map settings: reasoning off, `num_ctx` 65536, `num_predict` 4096, temperature 0.7, 40 iterations, HTTP timeout 240 s, episode timeout 1,800 s, round-2 oracle with retry, scorer v2.0 (`c6b02716...`).
- **Cells:** the 18 loss-map development tasks (stage 3: `u3 p3 h4 v2`; e1h: `e1h_amb_1 e1h_amb_2 e1h_abs_1 e1h_abs_2 e1h_chg_1 e1h_chg_2`; name-fix: `nf_single_1 nf_single_2 nf_multi_1 nf_multi_2 nf_amb_1 nf_amb_2 nf_exact nf_absent`) x 4 models (`lfm3:1.7b`, `qwen3.5:9b`, `gpt-oss:20b`, `bonsai-2:4b`) x new seeds **9 and 10** = 144 per arm, **288 episodes**.
- **Order:** 12 fixture sessions (model x environment); both arms of a cell adjacent; (task, seed) cells shuffled with a seed from the master seed 20261120 and the session key; arm order alternates with the cell position. The plan is `run_listval.py::plan_for("listval")`, its SHA-256 is frozen in `exam_queue/specs/listval_spec.json` (`6ba25045...`); the queue refuses to run if it differs.
- **Machine:** the laptop (RTX 4080 Laptop 8 GB, Windows Ollama 0.40.16), one GPU job at a time, queue run name `listval`, GPU-state block and contention rule of `exam_queue/gpu_state.py` active (under WSL `nvidia-smi` lists no processes, so a clean record is weaker evidence). Contended or infrastructure-failed episodes are retried by the queue and never become results; every other episode, including failures, stays.
- **Smoke first (not in totals):** `listval_smoke` (`smoke_spec.json`): qwen3.5:9b, task `h4`, seed 99. The prompt says 2 episodes, LISTVAL; this smoke runs **h4 under LISTVAL and under FULL** (two episodes) so that the switch-off path is also exercised. A smoke that never produces an inline list does not test the arm; then one more smoke on `e1h_amb_1` (also seed 99) is run and reported. A failed smoke is fixed and re-run before the measurement; no measurement setting changes.
- **Results log** `RESULTS_LOG.jsonl` from the first episode (queue); raw runs under `research/_artifacts/exam/listval/` (git-excluded).

## 3. Measures (analysis script `analyze_listval.py`, written and hashed before any measurement trace is opened)
Definitions use the saved traces (parser `offline_replay_20261116/episodes.py`; handler events `listval_inline`). Names are compared with a leading slash added.
- **Inline list** = a `listval_inline` event with parameters (rendered). **Shown instance** = (episode, request r, node, parameter) of one inline list.
- **PRIMARY (event level; decides the class):** per model, in LISTVAL episodes, **share of shown instances later fetched by `param_get` on the same node and parameter** = instances with at least one `param_get` call (any outcome) of that node and parameter in a request later than r, divided by all shown instances. **Excluded from numerator and denominator:** instances of the scripted-change parameter (`task["change"]`) in `e1h_chg_*` tasks (re-reads after the change are required). **Adoption met** = share <= 50% in >= 2 models, each of those models with >= 5 inline lists.
- **Descriptive companions (frozen now, not deciding):** (a) the same share restricted to shown parameters that are task-needed (a `param` support fact of the task); (b) share of inline lists after which at least one shown parameter of that node is fetched; (c) in the FULL arm, share of successful `param_list` calls with a node followed by a `param_get` of that node (the habit LISTVAL addresses); (d) inline lists, shown instances, `<unreadable>` values, cap fallbacks.
- **Secondary (per episode, paired by cell = task x seed x model, difference LISTVAL - FULL):** `param_get` calls (entity-expanded), model requests, input tokens, output tokens, native operations, wall seconds: per model and pooled, mean difference, median difference and the numbers of cells lower / equal / higher; supported-complete per arm (per model and total); exact; episodes ending without an answer. All of the above again with **name-rewrite v2 applied offline to the final answer of both arms** (`name_fix_applied_20261117/namefix_rule.py`, unchanged, ledger = task text + successful results, scorer v2.0): a second column, never a substitute.
- **Noise note stated beside any request comparison:** the identical-configuration FULL arm differed between the loss-map seeds 5-8 and the replication seeds 3-4 (same tasks and models): supported 84.4% vs 86.8%, requests per episode in the loss-map report vs `thinking_escalation_20261119/REPORT_REPLICATION.md`; the report quotes both per model and compares the FULL arm of this run with them.
- **Harm:** (H1) total supported-complete of LISTVAL < FULL - 3 (of 144 per arm); (H2) any `e1h_chg_*` LISTVAL episode that **reports a pre-change value taken from an inline list**, operationalised as: an inline list showed the scripted-change parameter of the change node, and the answer's `final_*` key equals `task["change"]["initial_value"]`. Every such episode is listed with its trace path and counts as harm.
- **Classes (decided in this order):** **C** = harm (H1 or H2). **B-** = adoption not met. **A** = adoption met and mean requests per episode lower for LISTVAL in >= 3 of 4 models and no harm. **B** = adoption met, no harm, and not A (state the direction in each model; the noise note is quoted). A model with fewer than 5 inline lists does not count toward adoption.

## 4. Limits stated in advance
Development tasks, one environment family per task group, tasks and models used for design; four models of different sizes with 36 paired cells each; counts are not independent samples; gpt-oss's thinking level cannot be controlled; laptop only (partial CPU offload for qwen3.5 and gpt-oss); one draw per seed, so run-to-run variation is not measured beyond the quoted noise note. The test shows whether models skip `param_get` when values are inline and what that does to cost; it does not show the effect on held-out tasks, and the prompt-only control is not run. The primary measure counts every shown parameter, so a model that fetches only the one parameter it needs scores a share below 50% even if it ignores the inline values for that parameter; companion (a) restricts to task-needed parameters for that reason.
