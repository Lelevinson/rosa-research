## 3. Interpretation (hypotheses; the class is the frozen one)
1. **Models do use the inline values when they see them:** in three models 79% to 100% of shown parameters are never fetched (bonsai 0 of 107, lfm3 1 of 49, qwen3.5 8 of 38). The adoption bar is met; qwen3.5 still re-fetches two thirds of the parameters it needs (6 of 9), so its habit changes least.
2. **The effect on cost is small and partly offset:** fewer `param_get` calls (-0.24 per episode) and fewer input tokens (-8.9%) come with more native operations (+11%: LISTVAL reads every parameter of every inline list) and more wall time; request counts fall in two models, are unchanged in qwen3.5 and rise in gpt-oss (more cells higher than lower, 12 vs 4; gpt-oss made only 1 inline list, so that increase is not caused by the mechanism's use and looks like run variation). None of the request or token differences is larger than the FULL arm's own movement between runs (noise note).
3. **Class C comes from the scoring rule, not from wrong answers:** exact answers are equal; the facts "not read" are facts the trace shows inline. A candidate that changes where values appear in a trace interacts with a scorer that credits only `param_get` rows; the post-hoc column shows what the comparison looks like if the owner decides inline values are reads (then the frozen rule would give B: adoption met, requests lower in 2 of 4 models, no harm). Not a result of this study, because that reading was fixed after the data.
4. **The list-sweep precedent is repeated in kind, not in size:** fewer tokens, more native operations, no demonstrated overall benefit.

## 4. Limits
Development tasks only (18; the ambiguity tasks hold most inline lists), four models with 36 paired cells each, one draw per seed; per-model differences of a few tenths of a request are within the quoted run-to-run movement. gpt-oss's thinking level cannot be controlled and its list use is minimal. Laptop only (CPU offload for qwen3.5 and gpt-oss). The scorer rule above makes the frozen supported counts a statement about "re-fetched facts", not about answer quality. The prompt-only control (tell the model to call `param_get` directly, or not to call it) was not run, so nothing here separates "the tool output carries values" from "the model needs less guidance". No teammate context was read for this run.

## Open search (other patterns noticed; counts and trace paths; unfiltered)
1. **Scorer credit rule:** 14 LISTVAL episodes are "not read" only because the value was inline (list above); the same rule would affect any mechanism that shows values without `param_get` (`posthoc.json`, `rescued`).
2. **Transient parameter-service timeout inside a list result** ("Wait for service timed out waiting for parameter services for node ... eclipse"): 2 episodes, `.../block_0006/005-nf_amb_1-LISTVAL-qwen3.5_9b-s9`, `.../block_0006/017-nf_amb_1-LISTVAL-qwen3.5_9b-s10`; the original (FULL) result of such a call is also a list with an error line, so the model sees an odd entry in both arms.
3. **bonsai FULL arm requests moved 7.99 / 9.14 / 12.47 across three runs** of the same configuration (loss map, replication, this run), with 4 more supported episodes than the loss map on 36 cells; the run order and seeds differ, so this is noise or drift, not diagnosed.
4. **gpt-oss losses unrelated to the mechanism:** `v2` no answer x2 (one `ResponseError` tool-call parse error where the model wrote its plan and a JSON fragment, `block_0007/009-v2-LISTVAL-gpt-oss_20b-s10`) and `p3` x2 with a slashless node name. Whether these failure types are as frequent in FULL was not checked beyond the paired counts.
5. **LISTVAL did not reduce the model's own mistakes:** lfm3 `e1h_chg_2` s9 answered `first_mode: run` although the list shown at request 2 said `idle` (it re-read after the change and overwrote its first value).
6. **Native-operation cost is real and visible:** 29 of 144 cells have more native operations under LISTVAL, 5 fewer; bonsai 11.0 to 12.9 per episode.
7. **Process:** `systems.py` and the exam-queue spec folder gained entries for this test (both committed, noted in the commit); the smoke queue sessions had to be closed by hand (`tmux kill-session`) because their runner window waits for Enter.
