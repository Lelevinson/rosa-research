## Job 1: name-keyed lookup
Per-entity read tools (schema-based, as in round 2): `ros2_param_get`, `ros2_param_list`, `ros2_node_info`, `ros2_topic_info`, `ros2_service_info` (not `ros2_topic_echo`). Entity kind = node for `ros2_node_info`/`ros2_param_list`/`ros2_param_get`, topic for `ros2_topic_info`, service for `ros2_service_info`. A ledger name has a kind if it was listed by `ros2_node_list`/`ros2_topic_list`/`ros2_service_list` or was the entity of a successful per-entity call (kind from that tool); other ledger names have no kind and are not used.
- **Dead-end trigger** (as written): a successful call of a per-entity read tool T on entity e, whose result text contains no full name other than e (names by the answer gate's rule). At most one firing per (episode, e).
- **Action**: run the other per-entity read tools T' != T that apply to a ledger entity x of the right kind, over ledger entities in first-seen order, tools in the order above, **at most 20 runs**; `ros2_param_get` is not run (its parameter name argument is not known; stated limit). From the outputs keep **only the lines that contain e's exact full name** (name boundaries: not preceded or followed by a name character or `/`); each line is shown with its source ("T' of x: line"). The system never picks an answer.
- **Measures**: firings (per tool, model, task); runs and not-computable runs; lines added; tokens added per firing = characters / 4 of the appended text, counted once for every request after the firing that is still needed (requests after k minus covered requests, as in the snapshot replay's accounting); **covered request** = a request after the firing with at least one call, no `final_answer`, in which every call is a successful per-entity read of some (T', x) that the lookup ran at the firing *and* that appended at least one line, and whose recorded result contains e's full name (the added line already shows what that call would show); predicted requests saved = covered requests; predicted tokens saved = recorded input+output tokens of covered requests. Overlap with sweep completion's V1 triggers: firings in episodes that have at least one V1 trigger in `offline_replay_20261116/results.json` (episode-level; request-level overlap is not computed). **Harm** = a firing whose appended lines name a look-alike of e: a different full name whose final path segment equals e's final segment or differs from it by edit distance 1; every harm case is listed with its lines. The single biggest task's share of the saving is reported.
- **Optional start trigger (evaluated separately)**: before request 1, the three list results of the environment (`snapshots.json`) are used to add one block that maps each task-text word (alphanumeric/underscore tokens) equal to a full name or a final path segment of a listed entity to its full name(s) and kind; two matches are both shown; a word with no match is not mentioned unless it looks like a name used as an entity argument somewhere in the task (not general as written: "no match stated as not listed" needs a rule for which words are candidate names, so only words that later appear as a **bare, not-found entity argument** in the recorded episode are scored as "not listed"). Block tokens = characters / 4, counted for every request. **Covered request** = at least one call and every call is either (i) a failed call whose entity is a task word the block maps or marks not listed, or (ii) a list-tool call whose non-empty pattern contains a task word the block maps.
- **Bar (frozen)**: the trigger variant passes if predicted requests saved >= 3% of all fixed-loop requests in the 400 episodes **and** predicted tokens added < predicted tokens saved; harm count and every harm case are reported regardless; a result carried by one task (largest task share > 60% of the saving) is flagged as not general.

## Job 2: no-progress cutoff
- **Progress** of a request: it adds a new name to the ledger (successful results only), **or** one of its successful calls is a first-time call (its (tool, other arguments, entity) was not executed successfully before in the episode), **or** a repeat of an earlier successful call returns text different from that earlier result. A request with only failed calls, only repeats with identical results, only `final_answer`, or no call is no-progress.
- **Rule**: if K consecutive requests, ending at request j, are all no-progress, the system offers only the finish tool at request j+1. K = 3, 4, 5, each evaluated on its own; the first time the condition holds in an episode counts.
- **Exact effects**: nothing before request j+1 changes. Requests removed = recorded requests with index > j+1 (request j+1 itself is spent on the finish call, and recorded requests up to the end of the episode, including the recorded final one, are removed if beyond j+1); tokens removed = their recorded input+output tokens. An episode is **cut** if at least one request is removed; **supported episodes cut** = cut episodes whose recorded answer was supported (scorer v2.0 label as recorded). Also reported: episodes where the rule would fire at j+1 = the recorded final request (nothing removed). The answer after a cutoff is unknown, so only cost effects are reported.
- **Bar (frozen)**: a K is eligible only if supported episodes cut = 0 (harm bound). Per model and total.

## Job 3: parallel calls in the list arm
Per request: number of native tool calls = tool calls of the model response excluding `final_answer` (list-argument items counted as one call each as parsed and also, separately, as one call per call), for C1+LA vs C1 (and C1+AG+LA secondary), per model: distribution (0, 1, 2, 3+), mean calls per request, share of requests with at least two calls, total calls and requests. Question 1: does the list arm show more parallel calls per request? Frozen reading: **yes** if the mean calls per request is higher by >= 0.10 in the pooled data and in at least 3 of 4 models. Question 2: can it explain the -71 requests? Counterfactual: requests the list arm would have needed for its own total number of calls at the control's pooled calls-per-request; the share of the recorded request difference (control minus list arm) recovered by it. Frozen reading: **explains** if the counterfactual difference recovers >= 50% of the recorded difference. Also: the same numbers split into episodes with and without a list-argument call (round 1 REPORT's split).
