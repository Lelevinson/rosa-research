# Classifier refinements made while developing on development traces (dated 2026-11-20 00:24 (laptop clock), before any measurement trace was opened)

Written after `classify.py` was run on the 230 existing development FULL episodes (part A and the replication, seeds 1-4: `labelled_dev.jsonl`, `TABLES_dev.md`) and hand-read on about a dozen of them, and **before** the measurement traces (seeds 5-8) were read; the queue's status counts were the only thing read from the running measurement. These refinements replace the wording of [PROTOCOL.md](PROTOCOL.md) section 3 where they differ; the protocol file itself is unchanged (SHA-256 in `PROTOCOL.sha256`).

1. **Accepted final answers are not format errors.** The parser's harness-text pattern also matches the success text "Answer recorded"; a first version therefore labelled every final answer `format` (found by reading u3 and h4 episodes). `is_rejected()` now judges the finish call by its own text (`Answer not accepted`, `final_answer needs`, `Invalid arguments`).
2. **`serial_batchable` needs independence from the previous request.** First version: "entities known before the previous request". That labelled necessary chain steps (u3: the publisher named by the previous result) as batchable, because a node list earlier had made the name known. Now a call is independent if it has no entity argument, or its entity is named in the task text, or the entity was in the ledger before the previous request **and** the previous request's results do not mention it. Still a detector: it cannot know why the model chose an entity.
3. **`loop` is a flag, not a type:** a request containing a call signature (tool, entity, arguments; successful or failed) that occurs for the third time or more in the episode. The protocol's "three consecutive repeat requests" missed the alternating pattern seen in a bonsai v2 episode (repeat, guess, repeat, guess, 40 requests).
4. **Failure types added/clarified:** `no_answer_cap` also when the episode has 40 requests (older rows do not carry the cap in `aborts`); `no_answer_format` when the last request was rejected by the harness and nothing followed; `wrong_conclusion_facts_present` is sub-split by the scorer's issue strings (`name_form`, `wrong_entity`, `answer_shape`, `wrong_value`; a heuristic, a typo such as `/nf/lanent/talon` counts as wrong_entity).
5. **Reconciliation of the floor:** requests above the floor are attributed to waste types in precedence order; `unexplained_longer_route` and `waste_within_floor` are reported so that the rules cannot hide a mismatch.
6. **Known weaknesses (not fixed, stated):** the floor in the task files assumes serial chains and one entity per request, so a model that batches correctly can fall below it (`below_floor`); the name ledger knows absolute names only, so a short name given in the task text and used as an argument counts as a guess (this is the name-binding problem itself, not a classifier error); `serial_batchable` counts a needless list call as batchable.

From this point `classify.py` is frozen: its SHA-256 is in `FREEZE_ANALYSIS.json`, and `classify.py lossmap` refuses to run if the file differs.
