- **Seeds:** `OPEN` between 2 and 3 per cell (sizing in section 8). Seeds are fixed in the manifest before the run; the same seeds for every system.
- **Run once.** Each cell is run once per system. A cell is re-run only if it is on the pre-declared infrastructure list: no model request was made (fixture, oracle, worker crash before the first request). The re-run uses the identical cell and is logged next to the original. A cell that made a model request is never re-run, whatever its outcome.
- **Three separate invalidation classes (replaces the single rule of revision 1, which let one paragraph both allow only pre-request retries and invalidate residual motion that can arise after a request):** (a) **pre-start reset or fixture failure** (before the first model request: failed reset, residual motion at the stable-state check, oracle not readable): infrastructure; the cell is re-run once, both runs are logged; (b) **agent-caused unresolved motion** (a goal dispatched by the agent is still active, or residual motion remains at the end, after at least one request): an agent outcome, **never re-run**, scored as a failure with its own failure class (section 5); (c) **post-start oracle or simulator loss** (the independent state reader or simulator fails after a request was made): the cell cannot be re-run under the run-once rule and cannot be scored; it stays in the denominator as `unscored`, results are reported with it counted as failure and with it excluded, and the same rule applies to every system; a share of `unscored` cells above 3% of a system's cells stops the study for a decision by the owner.
- **Scheduling:** one fixture session per (model, environment) with all systems and seeds of that session shuffled together under a master seed; one GPU/ROS job at a time.
- **No task, scenario, scorer rule, prompt or schema change after the first held-out request.** A legitimate protocol revision would be written, hashed and reported separately with its own results.
- Action tasks follow the spec: reset and stable-state check before each episode (class (a) above on failure); success judged by an evaluator-side ground-truth reader, never shown to the model; "claims arrival but did not arrive" counted separately. **Design from the review:** turtlesim verifies the executor and the judge; Gazebo/Nav2 tests whether the same loop transfers; each eligible arm gets the same typed action tool, authorisation, budget and deadlines; tasks include cases where a **fresh observation determines the goal** and cases where a **failed or cancelled action must be reported truthfully**; the runner logs the observation, the dispatched goal, the terminal status and the independent simulator state; for ordered actions the ordered events are scored as well as the final pose; for read-then-act the judge verifies that the read happened before the dispatch and the source value is varied between episodes (the dev judge v1.2 checks final pose and answer, so it can credit a skipped first step or a guessed constant: judge revision needed before exam use). The 10-task action pool is reported **descriptively** (no significance claim).

## 5. Metrics
- **Primary (correctness):** supported-complete using scorer v2.0 for inspection and reads and the custodian's frozen scorer for Nav2 inspection. Action tasks require independent final-state and truthful-answer checks plus [action judge v1.2](../action_dev_switch_20261118/judge_v1_2.py). Before exam use, freeze the per-step contracts and runner event capture with the custodian. Score actual dispatch and completion in order. For a read-derived goal, require a successful read from the bound source before dispatch and check that the command matches the recorded value under the frozen conversion. If calls were preselected together, record which results were available at selection.
- **Cost:** model requests, input tokens, output tokens, tool calls (native ROS operations) per episode and total. Wall-clock time is not a goal metric (contract).
- **Per model, always.** Every table has one row per model and a pooled row. The weak models dominate the unsupported cells and the long episodes, so a pooled number alone is not reported.
- **Failure classes, reported separately (not lumped into "capped").** One row per system and model for each of: **iteration cap** (ended at the 40-iteration cap, read from `episode_end.answer`), **backend parse error** (`ResponseError`, XML or tool-call syntax), **timeout** (HTTP, episode or worker), **no-answer text ending**, **wrong or unsupported answer** (answer given, scorer says unsupported), **guard-blocked or rejected write attempt**, **agent-caused unresolved motion** (action tasks), **unscored** (class (c) above), **infrastructure** (class (a)). The taxonomy is frozen with the exam; an episode has exactly one ending class and may carry several flags.
- **Totals with and without capped runs.** For this one total only, "capped" is the union of the classes iteration cap, backend parse error, timeout and no-answer ending (the individual classes above are always shown too). Report cost totals and supported rates **with** all episodes and **without** capped ones, plus the number of capped episodes per model and system; a system must not look cheaper because its failures ended early, nor more expensive because one model looped (dev totals are dominated by a few bonsai episodes). The cap ending is read from `episode_end.answer` (the executor reports "Agent stopped due to max iterations." without an error).
- **Ending class** per system: accepted finish call, text answer, no answer (dev counts: 362 / 35 / 19 of 416 FULL-type episodes).
- **Harness exposure counters** per system: rejected calls, blocked write attempts (dev: 76 write attempts, 61 of them under the stock executor), repeated identical calls.
- **Confidence intervals:** 95% intervals by a **cluster bootstrap over tasks** (a task is the unit; its seeds and models travel with it), per model and pooled; paired differences between systems on the same cells. Cell-level binomial intervals are not used as the headline because tasks repeat across seeds and models.
- **Success criteria:** `OPEN`, to be written at the freeze. Candidate form (not adopted): the method is at least as correct as E1 within a margin delta and cheaper by at least x% in requests or tokens, per the pooled and per-model rows. Delta and x cannot be chosen smaller than the detectable effects in section 7.

## 5b. One frozen primary comparison and cost endpoint (proposal for the freeze; the margin and its justification are the owner's)
- **Primary comparison:** M against E1 on held-out v2, all four models and all seeds pooled, one paired difference in **supported-complete rate** (M minus E1) over the same (task, model, seed) cells, with the **task as the cluster** (cluster bootstrap over the 76 tasks; a task's models and seeds travel with it). Everything else (S0, F, MT, ablations, Nav2, action tasks, per model) is secondary and labelled so.
- **Correctness margin (proposal, `OPEN`):** a non-inferiority margin delta on the supported-rate difference, M is "not worse" if the lower bound of the 95% interval is above minus delta. The dev noise limits what can be shown: the detectable difference with 76 tasks and 12 cells per task is about 4 points (section 7b), so a margin below about 4 points cannot be tested; a practically justified margin has to be chosen by the owner and stated with its reason before the freeze (this draft does not choose it).
- **Cost endpoint (primary):** **total input + output tokens over all assigned episodes** (capped, failed and unscored episodes included), as the **ratio M / E1 of totals**, cluster bootstrap over tasks; reported next to it: **requests per supported completion** (total requests / supported episodes) for each system, medians per task and the largest-tail episodes. Heavy tails (a few long bonsai episodes) are shown, not trimmed. Native ROS operations and any supervisor-side reads are counted for every system.
- **Descriptive only:** the 10-task action pool; per-model rows; Nav2 pools.

## 7. Power note: what the dev noise lets us detect
Source: `power_inputs.py` and `power_inputs.json` in this folder (saved logs only). The same fixed loop was run six times on the same 40 development cells (pilot C1 x2 seeds, round-1 C1 x2 seeds, ablation FULL, compaction FULL):
- **Supported cells per run: 36, 32, 35, 35, 32, 35 of 40** (mean 34.2, SD 1.72 cells = 4.3 points). Two runs of the loop flip the supported flag of **15.8%** of cells (mean over run pairs), i.e. a per-cell variance of about 0.079, which reproduces the observed SD.
- **Requests per 40-cell run: 211, 218, 222, 264, 195, 311** (CV 18%); **tokens** CV 22%. The spread is driven by a few long bonsai episodes (the 311-request run has the same loop as the 195-request run). The per-cell log-ratio of requests between two runs of the same loop has an SD of 0.54.
- **Detectable effect (two arms, 80% power, two-sided 5%, normal approximation, cells treated as independent):**

| design (cells per arm) | supported rate | supported cells | requests (mean per-cell ratio) |
|---|---:|---:|---:|
| dev, 40 cells | 17.6 points (31.3 at worst-case noise) | about 7 of 40 | 27% |
| the finish-split run, 80 cells | 12.5 points | about 10 of 80 | 19% |
| one model, 110 tasks x 3 seeds = 330 | 6.1 points | | 8.7% |
| 4 models x 110 tasks x 1 seed = 440 | 5.3 points | | 7.5% |
| 4 models x 110 tasks x 3 seeds = 1,320 | 3.1 points (5.4 worst case) | | 4.3% |
| held-out v2 only, 4 x 76 x 3 = 912 | 3.7 points (6.6) | | 5.2% |
| Nav2 inspection, 4 x 24 x 3 = 288 | 6.6 points (11.7) | | 9.4% |
| Nav2 read-then-act, 4 x 10 x 3 = 120 | 10.2 points (18.1) | | 14.9% |

- **Reading.** (i) Differences of 3-4 cells of 40 in the dev studies are noise, as the team already treats them. (ii) The earlier finish-tool gap (-7 of 40, 17.5 points) sits at the dev detection limit; it is plausible but one run cannot confirm it. (iii) On the full held-out set a pooled difference of about 3-5 points in supported rate and about 4-5% in requests is detectable; per model the limit is about 6-11 points, so per-model claims need larger effects or more seeds. (iv) The 10 read-then-act tasks can only support a descriptive statement with a wide interval, not a significance claim. (v) These are lower bounds on the noise: they ignore task-by-system interaction, heavy tails and model differences, which the task-level bootstrap in section 5 captures and these figures do not. (vi) **A flag on the finish-split protocol:** its reading rule treats a gap of 6 or more of 80 as "separated", which is below the 10 of 80 this note says can be detected; its conclusions must therefore be read as patterns, not detections. **Added 2026-11-19:** the finish split also **confounds the structured ending with the invalid-answer retry**: `LINE_JSON` removes the `final_answer` tool and with it the harness's one-retry rule for an invalid `final_answer` (the second submission is accepted as it is), so a difference between `FULL` / `TOOL_ONLY` and `LINE_JSON` mixes "structured ending" and "invalid-answer retry"; the split does not isolate either. The finish tool stays a design choice (not a demonstrated component), and any exam arm that removes it should keep or remove the retry explicitly.

## 7b. Task-clustered sizing of the primary comparison (revision 2)
The 3.1-point and 4.3% figures above treat cells as independent and the request figure concerns a per-cell ratio, so they do not size a task-clustered comparison of total cost. `power_clustered.py` (saved dev logs only, output `power_clustered.json`) uses the dev analogue of "M against E1" (the fixed loop, pilot arm C1, against fairness E1: the same 10 dev tasks x 4 models x 2 seeds = 80 paired cells):
- Supported: 65 against 65 (pooled difference 0.0 points). Per-task paired differences have an SD between tasks of 0.112 (as a proportion); the within-task cell noise is 0.433 and the estimated between-task component is 0.0 (floored at zero; the spread of the 10 task means is smaller than the within-task noise predicts). **Detectable supported difference (two-sided 5%, 80% power, normal approximation): 76 tasks x 12 cells per task about 4.0 points; 76 x 8 about 4.9; 76 x 4 about 7.0; 110 tasks x 12 about 3.3; 24 Nav2 tasks x 12 about 7.1; 10 tasks x 12 about 11.1.** With a zero between-task component the clustering costs almost nothing in this analogue; the held-out between-task spread is unknown and 10 tasks give a very rough estimate, so treat these as planning figures, not guarantees.
- Cost: pooled token ratio M / E1 **0.396** (requests ratio 0.822); per-task token ratios 0.215-0.820 (all below 1); SD of the per-task log ratio 0.346, so with 76 tasks a ratio outside about 0.90-1.12 is distinguishable from 1; the dev ratio of 0.4 is far outside it. The bootstrap interval over the 10 dev tasks is [0.34, 0.52] (illustrative, 10 clusters). The request ratio is closer to 1 (0.82) and heavier-tailed than the token ratio: the paper's strongest claim in the dev evidence is the token cost, as the review says.
- These supersede the independent-cell numbers for the primary comparison; section 7's table remains for the other designs.
