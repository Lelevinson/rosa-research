## 3. Queue
**Priority tiers (owner's decision of 2026-11-19; any stopping point is usable):** (1) **M against E1 on held-out v2 and on the turtlesim held-out pool**; (2) **S0 and F on those pools, plus M, E1, S0 and F on the Nav2 pools**; (3) **ablation arms on held-out v2 (option C complete)**; (4) **ablation arms on the Nav2 and turtlesim pools plus a third seed everywhere (option B complete)**. `specs/exam_spec_TEMPLATE.json` encodes exactly this (tiers 2 and 4 are split into 2a/2b and 4a/4b so that no cell id appears twice). The turtlesim held-out pool has no runner yet (see the template's notes).
- **Order inside a tier:** seeds in the tier's order, then tasks (seeded shuffle), then models, then systems (seeded shuffle inside the pair). All systems of a (pool, task, model, seed) **pair run next to each other**, so a stop leaves complete pairs.
- **One GPU job at a time:** the runner is single-threaded; before each block it unloads every Ollama model except the one needed. Do not start anything else on the GPU (Gazebo included) while it runs.
- **Blocks:** the next unfinished cell in priority order plus the following unfinished cells of the same (tier, seed, model, environment), up to `block_size` (default 48). One block = one fixture session = the existing `run_pilot.session` (oracle before / every 12 episodes / after). **Measured session overhead: about 160-270 s per session** (66-103 s of setup before the first episode, the rest the oracle checks and shutdown; from the 8 sessions of the nudge run), i.e. 13-25% of the work at 16-24 cells, about 14% at 48.
- **Cell id** = `pool|task|system|model|seed`. A cell is finished only when its full row has been appended (flush + fsync) to `RESULTS_LOG_<machine>.jsonl`; the id is the dedupe key.
- **Resume = start the same command again.** At start the runner (1) kills orphan episode workers of this run (a hard kill of the runner leaves the worker running in its own session; tested), (2) logs episodes that finished but whose row was not written (`recover`), (3) skips every logged cell, (4) re-runs the rest. A killed episode has no row and is simply run again in a new block folder; its partial trace stays in the old block folder.
- **Stop gracefully:** `touch research/_artifacts/exam/RUN/STOP` (the runner finishes the current episode, then exits; remove the file to resume).
- **Specs:** `queue_core.py plan --spec SPEC --machines laptop:0.4,lab:0.6` prints the cells per tier and machine and warns about systems without an adapter.

### Proposed rule for a runner or machine crash (needs the owner's approval at the freeze)
The exam protocol says a cell that made a model request is never re-run. A **crash of the runner or machine** (no `episode_end`) is not an agent outcome: the partial episode is discarded, kept in its block folder, and the cell is re-run once with the identical seed. This is symmetric across systems and is independent of the outcome (a crash cannot select for failures). The count of such re-runs is reported per system. This is a proposal; the owner decides.

### Two machines (laptop and lab) without duplicate episodes
- **Static split by pair.** `--machines laptop:0.4,lab:0.6` maps a hash of the pair (pool, task, model, seed) into [0, 1) and gives each machine its range; all systems of a pair stay on one machine. Both machines must use the **same spec file** (its SHA-256 is written into every row and `merge-check` flags rows from another spec) and the same share string. Tested: disjoint, complete, pairs together, about the configured share.
- **Do not change the shares after results exist unless the logs have been exchanged first.** Ownership is by hash, so new shares reassign some pending cells and could reassign cells the other machine already finished. Procedure: stop both runners, copy each machine's `RESULTS_LOG_<machine>.jsonl` to the other, start both with the new shares (a runner skips every cell found in any log present locally), run `merge-check` at the end.
- **The lab is the primary machine.** Suggested shares for a two-machine exam: `--machines lab:0.8,laptop:0.2` (the owner sets them from the mini-exam speed ratio, checklist step 8). If the lab is the only machine, use `all` or `lab:1`.
- **Same conditions:** same model digests (`ollama list`), same Ollama version, ROS 2 Jazzy, domain 220, same settings. Run the mini exam (section 9) on the lab computer first and compare episode times with the laptop's table.
- `queue_core.py merge-check --spec SPEC --run-name RUN --machines laptop:0.4,lab:0.6` reports duplicates, rows outside the spec, missing cells, pairs with only some systems, rows logged on the wrong machine and rows from another spec.

## 4. Health, cleanup, status, commits
- **Ollama:** checked before every episode (`/api/tags`); before a block the runner waits up to 30 minutes for it to return (state `waiting_for_ollama`) and then stops with state `blocked_ollama` and exit code 3. The monitor reports "Ollama down" after 2 minutes.
- **Disk:** checked before each block (default minimum 20 GB; the monitor alerts under 30 GB); below the minimum the runner stops with `blocked_disk` (exit 4). Raw traces under `research/_artifacts/` grow roughly with the number of episodes; check the free space before a long run.
- **Cleanup:** between episodes `ros2 ...` command-line children that outlived their episode are killed (only processes of our `ROS_DOMAIN_ID`; fixture nodes of the running block are not touched), and a per-environment reset command can be configured for Gazebo/Nav2 (`gazebo_reset_command`; **no Nav2 runner exists yet, so this hook is untested against a real Gazebo**). After every block, and after a failed block, all leftover fixture and ROS processes of our domain are killed (`health.kill_leftovers`: TERM, wait, KILL).
- **Heartbeat and status:** a thread rewrites `status_<machine>.json` every 30 s (state, tier counts, done/total, current tier:system:model, last progress, Ollama, free disk, GPU memory, quarantined groups). **Progress** is the newest of: a logged episode, or a write to the running episode's trace file, so a slow but live episode is not "stuck".
- **Quarantine:** a block group (model, environment, tier) whose block raises 3 times is skipped and reported ("a block keeps failing"); a cell that never yields a result 3 times is skipped. The run ends with state `finished_with_skips`. Skipped cells are listed in `failures_<machine>.json` and are not silently dropped: they appear in the final report as a failure class.
- **Git:** every 3 hours the monitor commits the compact tables (`exam_results/RUN/compact_<machine>.jsonl`, added with `git add -f` because `research/` is excluded) to the current local branch with a fixed message; **it never pushes** (pushing is the owner's decision).

### Shared GPU: per-episode GPU-state logging (implemented 2026-11-20)
Design and rule: `LAB_SETUP_CHECKLIST.md`, section "GPU sharing"; code: `exam_queue/gpu_state.py`; tests: `GpuStateTests`, `GpuQueueTests` in `exam_queue/tests/test_queue.py`.
- **Sampler (host):** `tmux new -d -s gpusample 'python3 .../exam_queue/gpu_state.py sample'` writes one JSON line every 5 s to `research/_artifacts/exam/gpu_state.jsonl` (set `ROSA_OLLAMA_URL` first; on the lab `source lab/lab_env.sh`). It must run on the host because the container has no `nvidia-smi`; the repo is shared, so the runner in the container reads the same file. `start_exam_tmux.sh` warns if the log is older than 60 s.
- **Per episode:** the runner takes its own snapshot at the start and end and adds the sampler's samples in between; the row gets a `gpu_state` block (first / last sample, min free VRAM, max VRAM held by processes that are not ours, residency `size_vram / size` at start and end, sample count). Our processes are the Ollama server found by its port plus its children.
- **Contention rule** (frozen design): contended if (a) another process held >= 1024 MiB, or (b) our model was fully resident when first seen and not at the end, or (c) the VRAM available to us at the start was below the model size. No samples = `unknown`, not contended. Where `nvidia-smi` lists no processes (WSL on the laptop) rules (a) and (c) cannot fire; the block says `process_info: false`.
- **Handling:** a contended episode goes to `CONTENDED_LOG_<machine>.jsonl` (full row) and `compact_<machine>_contended.jsonl`, is never a result, and its cell is run again (it counts toward the 3-try quarantine). Before every episode the runner waits up to `gpu_wait_seconds` (default 1800, state `waiting_for_gpu`; 0 = do not wait) until no other process holds >= 1 GiB; after the wait the block fails (retried later). `exam_tables.py` table 6 gives contended / started per machine and model.
- **Bug found by the test (fixed):** `recover()` re-read finished attempts without GPU data and would have turned contended episodes into results; it now skips attempts already kept as contended.
- **Limits:** a 5 s sampler can miss a shorter burst; compute contention without a VRAM change shows only as slower tokens/s; the thresholds are design choices, not measured optima; on the lab, `nvidia-smi` shows host pids, so our processes are told apart by pid, not by name.

**Queue pitfall found on the lab (2026-11-19), guarded since 2026-11-20:** `--machine lab --machines all:1` used to select zero cells and end `finished 0 0`. `queue_core.py run` now stops with a message (exit 1) when `--machine` is not named in `--machines` or owns 0 cells, and `notify_exit.py` writes a `crashed` status when no status file exists, so the monitor reports it. `merge-check --machines all:1` no longer reports every row as `logged_on_the_wrong_machine` (that was the lab dummy run: rows logged by `lab`, checked without `--machines lab:1`; `all:1` has no real owners, so the check is now "not checked" and any machine in the logs that is not in `--machines` is listed).
**Ollama address (step 8a, done 2026-11-20):** the runners, `health.py`, the probes and the checks read `ROSA_OLLAMA_URL` (default unchanged: `http://172.30.80.1:11434`). The container gets it from `run_container.sh`; the host monitor and sampler get it from `lab_env.sh` (`http://127.0.0.1:11435`); `start_exam_tmux.sh` passes it to the monitor explicitly and warns if `EXAM_EXEC` is set without it.

### Integrity check before every exam block (added 2026-11-19)
Run on the lab host (not inside the container): `bash <LAB_PATH>` (read-only; `--since "YYYY-MM-DD HH:MM"` lists files changed after that time, with the user). It checks: our container runs from the expected image id (host network, domain 220, localhost-only, custodian mounted read-only); image id and size; git HEAD and tracked files; a sha256 manifest of 1,065 repo files; no `research/.local`; Ollama version, loopback-only port, our binary, all 8 model digests; other containers, other Ollama servers and foreign ROS/Gazebo processes (FAIL if another container uses domain 219/220); modes and owners of our folders; free space; GPU processes holding 1 GiB or more. **Exit code 1 (any FAIL): do not start the block.** WARN lines need a human look (for example another user's container on the shared host). The baseline lives in `<LAB_PATH>` (`expected.env`, `expected_digests.json`, `repo_manifest.sha256`); it is rewritten only by `INTEGRITY_RECORD_OK=1 bash check_integrity.sh record`, after an approved change (for example after the step 8 code changes, after re-freezing). The check never opens the custodian folder (only its own mode and owner). Limits: all users share one Linux account, so "changed by whom" shows only `<LAB_USER>`; the manifest excludes results, logs, `.venv` and caches; a user with the same account could also change the baseline files. Guide for teammates: `LAB_GUIDE_FOR_TEAM.md`.

Read `tmux new-session -d -s NAME -n runner 'COMMAND'` as: create a session called NAME, detached (`-d`, it keeps running without a terminal), with a window (`-n`) called runner that runs COMMAND. `bash script ARGS -- --dummy` passes everything after `--` to `queue_core.py run`. `kill -9` is a hard kill that gives the process no chance to clean up; the queue is built to survive it.

## 7. Keeping a run alive on Windows (laptop, dev runs only; the exam runs on the lab)
- The tmux session lives inside WSL; closing a Windows Terminal window may or may not stop WSL. **Test it (section 8) before relying on it.** If it does not survive: create `C:\Users\user\.wslconfig` with `[wsl2]` and `vmIdleTimeout=-1`, run `wsl --shutdown` in PowerShell, and repeat the test; if still not, start a hidden keep-alive: `Start-Process wsl.exe -ArgumentList "-d","<distro name from wsl -l -v>","--exec","sleep","infinity" -WindowStyle Hidden`.
- Windows power plan: AC, never sleep, **lid close = do nothing**, active hours set so Windows Update does not restart the machine; keep the charger connected. Ollama runs on the Windows host: keep it running (it may start on login only).

**No progress for 15 minutes:** attach to tmux, look at the runner window and the newest `*.worker.log`; a hung `ros2` command is killed by the between-episode cleanup, a hung model request ends at the 90 s HTTP and 900 s episode limits.
**Hard stop and report:** at any time `STOP`, then `exam_tables.py`; the tier order guarantees complete (task, model, seed) pairs of the tier in progress and complete earlier tiers.

## 12. Mini exam result (2026-11-19, laptop)
Spec `specs/mini_exam_spec.json`: 2 dev tasks (`u3`, `e1h_abs_1`) x 2 models (`lfm3:1.7b`, `qwen3.5:9b`) x 2 systems (`M`, `E1`) x seed 1 = 8 episodes, started in tmux with the real runners (fixture sessions, oracle checks, one GPU job at a time). **Result: 8 of 8 cells logged once; `merge-check`: 0 duplicates, 0 missing, 0 outside the spec, 0 from another spec; no Ollama model and no process left; the monitor sent the "finished" message.**
- **Kill and resume on the real path:** after 4 episodes the runner was hard-killed (`kill -9`) while the cell `u3 / M / lfm3` was in flight. Its partial trace has no `episode_end` (block 3). Restarting the same command killed the orphan worker, found 4 finished cells, and re-ran the rest; that cell was run again once (block 5) and logged once. The 4 finished rows were not touched.
- **A defect found by this test, fixed:** the orphaned fixture nodes of the killed session (19 processes) still held the ROS domain, so the first retried session refused to start ("Domain not empty"); the runner's after-failure cleanup killed them and the next block ran (one group failure counted, 1 of 3).
