# Write-tool attempts, tail cost, repeat loops: frozen offline protocol

Dated 2026-11-18, Asia/Taipei. Written and hashed **before** any of these counts exists and before the counting script exists. Offline only (CPU, saved traces; no model, no ROS, no GPU). Development evidence only (synthetic fixtures, four small models); not held-out, not causal, not a novelty claim. Held-out custodian files are not opened. Request: owner message of 2026-11-18 (items 1-3). Population, parser and conventions are those of `candidate_counts_20261118` (`PROTOCOL.md` section 1-2; `count_candidates.py::load_population`, `parse_episode`; same 1,832 episodes, same infrastructure exclusions, scorer v2.0 unchanged). Episodes recur across studies and arms, so counts are **not independent samples**.

**Disclosure:** before writing this protocol I looked at the structure of the write-attempt records (tool names, argument keys, and the distinct output texts such as the guard message and pydantic validation errors) to be able to define the status classes. I had not seen counts per class. The earlier report already states 76 attempts and "no write command reached ROS" (fairness `RUN_NOTES`, S0 report); this protocol checks that from the traces rather than assuming it.

## Item 1. Write-tool attempts
**Attempt** = one recorded tool call (a unit of `parse_episode`) whose tool is `ros2_service_call` or `ros2_param_set`, in any population episode.
**Execution status** (first match, from the trace of that call):
1. `no_result_validation`: the call has a `tool_error` event whose text starts with `<n> validation error` and no `tool_end` (the stock executor ended the episode on it); the tool body did not run.
2. `validation_text`: the result text starts with `<n> validation error` (errors-as-text arms); the tool body did not run.
3. `guard_rejected`: the result is the observation-only guard's rejection (`{'error': 'Observation-only study: command rejected.'}`); the guard sits before the ROS command.
4. `not_available`: `Tool ... is not available in this session` (menu arm, tool not offered).
5. `executed`: anything else, i.e. a result that is none of the above (evidence a command reached ROS).
**What it would have changed** (inference from the arguments and from the saved results of the same environment, not an observation): fixture knowledge = names appearing in any successful result of any population episode of the same `env`, normalised `"/" + name.lstrip("/")`: nodes from `ros2_node_list`, services from `ros2_service_list`, parameters from `ros2_param_list`.
- `ros2_param_set` (`node_name`, `param_name`, `param_value`): `existing node, existing parameter` (would set a fixture parameter), `existing node, parameter not seen` (would fail or declare nothing), `no such node` (would fail; includes pseudo-nodes such as `/rosa` used as an answer store).
- `ros2_service_call` (`service_name`): `existing state-changing service` (name ends `/set_parameters` or `/set_parameters_atomically`), `existing read-only service` (ends `/describe_parameters`, `/get_parameter_types`, `/get_parameters`, `/list_parameters`), `existing other service`, `no such service` (name absent from every listing; would fail).
Report: per arm (study, arm), per model, per status and per would-change class, the number of attempts and of episodes with an attempt; the attempts in the 61 fairness stock-executor arms (E0, E1) separately; the same per-arm table for the method arms (C1, FULL, CONTROL and every other arm using the 12-tool menu): attempts = units naming a write tool plus `tool_not_offered` / `blocked_write_tool` handler events naming one, with the number of episodes.
**Bars.** B1a (data check): the count reproduces the earlier figures (76 attempts, 61 in fairness); otherwise report the discrepancy with the reason. B1b: the statement "no write command reached ROS in these traces" is made only if 0 attempts have status `executed`; if 1 or more, stop and report them with trace paths first.

## Item 2. Tail cost
Arms (episodes per arm on the same 10 development tasks x 4 models x seeds): **ORIG** = `s0` S0 (stock prompt, 47 tools, stock executor; 80 cells, seeds 1-2); **E0**, **E1** = fairness (80 each, seeds 1-2); **A1** = pilot A1 (stock executor, deconflicted prompt, aborts on tool errors; 80), reported as an extra row; **FULL** = pilot `C1` (80 cells, seeds 1-2, the same cells), with the other FULL-type runs as separate rows (round1 `C1` 80, ablation `FULL` 40 seed 1, compaction `FULL` 40 seed 1). "Matched tasks": all these rows cover the same 10 tasks; seeds are as listed (the ablation and compaction rows have seed 1 only); no cell is dropped or added.
Per arm and per model and pooled: per-episode **requests** (`llm_requests` of the log row) and **tokens** (input + output of the log row): median, p90 (nearest rank, `sorted[ceil(0.9 n) - 1]`), maximum, mean, total; **iteration-cap endings** (the `episode_end` answer, error or the row's `aborts` contains `max iterations`; also report the count with requests >= 40); the share of an arm's total requests that comes from its top-decile episodes.
**Bar B2** (only for the reading, not a filter): the tail is a candidate cost to attack if, for an arm, the top decile of episodes carries at least 25% of the arm's total requests **and** at least 5 iteration-cap endings occur over at least 2 models. The measured value of each condition is reported whichever way it falls.

## Item 3. Repeat loops
**Repeat** = a call that is `ok` (not a harness message), whose tool and arguments (canonical JSON) equal an earlier `ok` call in the same episode (the `identical_repeated_ok_call` detector of the candidate counts). **Episodes of interest** = episodes with 2 or more repeats. For the **first repeat** (at request `r`): `facts_present` = scorer v2.0's `support_missing(task, rows)` is empty for rows rebuilt from all calls of requests strictly before `r`, with the episode's own task `support` list; else `facts_not_yet`. Rows are rebuilt from the call items (tool, the entity argument put back into the arguments, output, text, ok); **data check B3a:** the same rebuild over all calls of the episode must reproduce the scorer's own `support_missing` for at least 99% of population episodes (otherwise the limitation is reported and the classification is labelled approximate).
Report per model, per arm group (stock executor arms: S0, A1, E0, E1; menu arms) and pooled: episodes of interest, first repeat class, how many of each class ended unsupported (`supported` false), with no answer (`answer` is None), and the number of requests after the first repeat (sum, median).
**Bar B3** (idea "stop repeating once the facts are present" kept for consideration): at least 10 episodes with `facts_present` over at least 2 models **and** at least 3 of them unsupported or without an answer. Measured values are reported whichever way it falls; the idea's mechanism (what a stop would do to the model) is a hypothesis this count cannot test.
