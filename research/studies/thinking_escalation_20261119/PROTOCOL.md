# Thinking escalation: live development protocol (frozen before any code exists)

Dated 2026-11-19, Asia/Taipei. Development evidence only (synthetic fixtures, four small models, authored dev tasks); not a held-out result, not causal beyond these cells, not a novelty claim. Scorer v2.0 unchanged (`c6b02716...`). Held-out custodian files are not opened; held-out aggregates are not used. Authorisation: the owner's message of 2026-11-19, step 2 (gate: per-request thinking toggle for at least 2 models; met, see [FEASIBILITY.md](FEASIBILITY.md)): write and hash the protocol, then a dev run with three arms, smoke first, `nohup`. Not a method component.

## 0. Preflight record (AGENTS.md; ROSA_RESEARCH_CONTEXT 12.2 / 14.2)
1. **Observed opportunity.** Failure moments are common in the loop: in the 1,832 saved episodes 594 (32%) contain a dead-end lookup result (dead-end lookup report: 38% of FULL-type episodes), the nudge run's 160 episodes had 42 identical repeats and 24 backend tool-call exceptions, and the fairness study found most of the fixed loop's gain is "errors are returned as text" (the model gets a second chance). 26 of the nudge run's 160 episodes were unsupported (bonsai 10, gpt-oss 9, lfm3 7). That error moments are where a small model's extra reasoning would matter is **a hypothesis**; no study here tested thinking at all (all earlier runs set `reasoning=False`; gpt-oss ignores it, see FEASIBILITY.md).
2. **Candidate vs control action difference.** Candidate: after an error, not-found, empty result or identical repeat, the system turns thinking on for the next 2 requests, then off. Control (strongest ordinary mechanism): thinking always on (ceiling and cost reference) and thinking always off (current). Observable difference: on a trigger event the next request is generated with a thinking budget under `ESCALATE` and without under `FULL`; the model's next action can differ (a changed call, a progress call, a `final_answer`).
3. **Closest prior mechanisms (not verified against original sources; mechanism-level neighbours only).** Reflection after failure in agent loops (Reflexion-style), adaptive or budgeted test-time compute and model cascades that escalate on failure. In this repository: the finish nudge (class B: a one-line text did not change weak models' loops), stall hint v2 (failed offline), errors-as-text (the existing recovery channel). The incremental difference is the compute allocation at the event (more reasoning, same information), not new information. No novelty claim.
4. **Fair evaluation and cost.** Three arms with identical prompts, tools, schemas, task, seeds and loop; only the per-request thinking setting differs. Thinking tokens are not reported separately by Ollama; the study reports total output tokens as logged and an estimate of thinking tokens (section 4). Wall time is reported because thinking changes it by 3-30 times per request (probe).
5. **Smallest decision-changing next action and stop rule.** One run of 240 episodes after a smoke. If class A: the owner may decide a second seed set / stock-executor version (not authorised here). If class B or C: drop escalation for this week. If `ALWAYS` shows no headroom (section 5, C0): report that thinking does not help these cells at all; escalation cannot then be shown to help. No re-run or rule change after the first live request.
**Status of the idea: not yet justified as a method component.** Known risks: (i) thinking tokens exhaust `num_predict` (4096) and leave an empty answer (counted as `length` cut); (ii) thinking changes tool-call formatting in these models (unknown); (iii) gpt-oss cannot be turned fully off, so its `FULL` is not "no thinking".

## 1. Arms
| arm | thinking setting per model request |
|---|---|
| `FULL` | pilot arm C1 exactly as in earlier runs: `reasoning=False` in the chat-model constructor, no per-request override (for gpt-oss this means the model's default low thinking that Ollama does not switch off) |
| `ESCALATE` | `FULL`, except that for the 2 requests after a trigger the request carries `reasoning=True` (lfm3, qwen3.5, bonsai) or `reasoning="high"` (gpt-oss) |
| `ALWAYS` | `FULL`, except that every request carries `reasoning=True` / `"high"` (gpt-oss) |
Prompts, tool schemas, tool descriptions and executor are byte-identical across arms (hash-checked in the smoke).

## 2. Trigger and window (frozen)
- **Trigger events**, each detected after a tool call in the arm's `execute` / `execute_extra` (same code and logged in all arms, acted upon in `ESCALATE` only):
  1. **error**: the call raised (tool failed, strict pre-check rejection, tool not available, blocked write tool, invalid final answer);
  2. **not-found**: a returned result whose text matches `episodes.NOT_FOUND` ("not found", "Unable to find", "does not exist", "no such") or that contains an `error` entry for an item;
  3. **empty**: an empty result (empty or whitespace text, `[]`, `{}`, `null`, `None`, a dict whose values are all empty containers or empty text such as `{"nodes": []}`, which is what the list tools return when nothing matches) or an `error` entry with an empty message;
  4. **identical repeat**: a successful call whose tool, arguments and result equal an earlier successful call (the `repeat_finish_nudge_20261118` definition).
  Class precedence when several apply: error, then not-found, then empty, then identical repeat. Backend-level failures (tool-call parse errors, HTTP timeouts) are not triggers (stated limit).
- **Window:** a trigger sets `remaining = 2`. Each following request with `remaining > 0` is sent with thinking on, then `remaining` decreases by 1. A trigger inside the window resets `remaining` to 2 (the window never exceeds 2 requests after the latest trigger). One fire is counted per request that contains at least one trigger (several triggers from parallel calls in one request are one fire; their classes are all logged).
- Every request logs a `think_request` event: request index, level sent (`None`, `True` or `"high"`), `remaining` before. Every call logs a `call_class` event: request index, tool, canonical arguments, class (`error`, `not_found`, `empty`, `repeat`, `ok`). All in every arm.

## 3. Design
- **Tasks (10):** stage 3 `u3`, `p3`, `h4`, `v2`; e1h `e1h_amb_1`, `e1h_amb_2`, `e1h_abs_1`, `e1h_abs_2`, `e1h_chg_1`, `e1h_chg_2`. **Models (4):** `lfm3:1.7b`, `qwen3.5:9b`, `gpt-oss:20b`, `bonsai-2:4b` (all four support per-request toggling; gpt-oss by level). **Seeds** 1 and 2. **Episodes:** 10 x 4 x 2 x 3 = **240** (80 per arm).
- **Scheduling:** one fixture session per (model, environment), arms and seeds shuffled together, master seed 20261125; 8 sessions. Settings as the earlier runs (temperature 0.7, `num_ctx` 65536, `num_predict` 4096, 40 iterations, round-2 oracle with the 5 s retry) **except** the time limits: HTTP timeout **240 s** and episode timeout **1800 s** for all three arms (earlier runs used 90 s and 900 s; a 4,096-token thinking response at about 35 tokens per second exceeds 90 s). This is a protocol choice, not a tuning after seeing results.
- Known validity defect carried unchanged: the `e1h_chg_*` hook misses when a node name is written without the leading slash.
- **Smoke (not in totals):** `qwen3.5:9b` and `gpt-oss:20b`, tasks `u3` and `e1h_abs_1` (the absent-node task produces not-found events), seed 1, three arms = 12 episodes. **Clean** means: all 12 end with `episode_end`, no worker error, none over the limits; prompts and offered schemas identical across arms; `FULL` requests have no `reasoning` override, `ALWAYS` requests all carry the override, `ESCALATE` requests carry it exactly for the 2 requests after each fire (checked from `think_request` and `model_start.options`); when the override is on, the response carries `reasoning_content` or the model returned an empty thinking (reported) and the answer content has no `<think>` tag; the logged trigger classes equal those recomputed from the trace by the analysis predicate; Ollama loaded only the expected model and it is unloaded afterwards. If no trigger occurs in the smoke the escalation path is reported as unexercised by the smoke and tested by unit tests only. An anomaly stops the study.
- Stop and report if Ollama is unreachable, three consecutive episodes fail for infrastructure reasons, or another job takes the GPU. Infrastructure-failed cells (no request made) are listed and reported with and without; none is dropped or re-run under a changed rule.

## 4. Measurements (frozen; applied by `analyze_think.py`, written and hashed before the full run)
Per arm, per model, per task and overall:
- **supported-complete** (scorer v2.0); **model requests**; **input tokens**; **output tokens** (as logged by Ollama, thinking included); **thinking-token estimate** per request = `max(0, output_tokens - ceil(len(content + json(tool_calls)) / 4))` (an estimate with the same formula for every arm and model; where `reasoning_content` is returned, its length / 4 is reported next to it); **wall seconds**; **cap endings** (`episode_end.answer` contains "max iterations"), **no-answer endings**, **timeouts**, **backend errors**, and **length-cut responses** (`done_reason == "length"`).
- **Fires** (all arms log the events; `ESCALATE` acts): fires by class and model; escalated requests and their output tokens (the cost of escalation) against the same quantity for non-escalated requests.
- **Per-event outcomes** (computed identically in all three arms at every trigger request `t` that has a request `t+1`): **O1** the first call of request `t+1` differs from the triggering call (tool or canonical arguments); **O2** request `t+1` contains at least one call of class `ok` (progress: a successful call that is not an identical repeat); **O3** request `t+1` calls `final_answer`; the same O1-O3 for `t+2`. Also whether the episode ended supported. Reported per class and per model, `FULL` vs `ESCALATE` vs `ALWAYS`.
- Paired cell view (task, model, seed): supported in both / `FULL` only / `X` only / neither, for `ESCALATE` and `ALWAYS` against `FULL` (descriptive: trajectories diverge from request 1).

## 5. Reading rule (frozen before any episode runs)
Conventions, not significance tests. From dev noise (about 15.8% of cells flip between runs of the same loop), the supported difference detectable with 80 cells per arm is about 10 cells; differences of 4-9 cells are not told apart from noise.
- **C0 headroom (ceiling):** `ALWAYS` supported minus `FULL` supported is 4 cells or more. If not, "no headroom seen in these cells": the class below is reported but a benefit of escalation cannot be argued.
- **Mechanism bar (M):** pooled over the trigger events with a request `t+1`, the share with **O2** (progress next request) is at least 10 percentage points higher in `ESCALATE` than in `FULL`, and higher in at least 2 of the 4 models, counting only models with at least 15 such events in both arms (others "not evaluable").
- **Harm flags (`ESCALATE` against `FULL`, any one):** supported lower by more than 3 cells of 80; model requests up by 15% or more; timeouts + cap endings + no-answer endings up by 5 or more; length-cut responses up by 10 or more.
- **Cost flag (reported, not a harm flag):** total tokens (input + output as logged) of `ESCALATE` at least 1.5 times `FULL`; wall seconds at least 1.5 times `FULL`.
- **Classes:** A = M met, no harm flag; B = M not met, no harm flag; C = a harm flag, M not met; D = M met with a harm flag. Class A means "eligible for consideration; a benefit in supported answers is claimed only if it exceeds the detectable difference, and the cost flag is reported". Every statement is limited to these 10 tasks, 4 models, 2 seeds and these fixtures. No change to the trigger, window, levels, scorer or scenario after the first live request.

## 6. Power note
Triggers are frequent in the weak models (hundreds of events expected over 240 episodes), so the event-level bar is well powered; the supported bars have no power below about 10 cells. `ALWAYS` is a cost and ceiling reference, not a candidate. gpt-oss's three thinking levels are not on/off, so its arm contrast is smaller than for the others.
