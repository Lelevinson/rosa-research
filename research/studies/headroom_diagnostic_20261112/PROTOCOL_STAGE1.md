# PROTOCOL_STAGE1 (frozen before any Stage 1 inference)

Frozen: 2026-11-12. Revisions after the first inference are listed at the bottom, never edited in place. All tasks are development evidence, not held-out. Claims are limited to these tasks, this fixture, these two models and one session.

## 1. Questions and hypotheses
- **1a (paired prompt-fix estimate).** H1a: on the same tasks, replacing ROSA's "never call multiple tools / do not batch" text with a plain permission reduces model requests per supported-complete episode without lowering the number of supported-complete episodes. Refuted if the paired difference is zero or negative or support drops by two or more episodes.
- **1b (width).** H1b: with the deconflicted prompt, requests stay within floor+1 and coverage stays complete as the number of entities grows to 32. Refuted at N=32 as in section 6.

## 2. Arms (both stages use the full stock ROSA 2 registry, 47 tools)
- `A_orig`: unchanged ROSA system prompts (hash recorded).
- `A0`: the single system message beginning "CRITICAL - SEQUENTIAL TOOL EXECUTION" is removed and one message is added: *"Independent tool calls whose arguments are already known may be made together in one response."* Nothing else changes (no efficiency guidance, no batch tool). Implemented as a subclass of `ROSA` overriding `_get_prompts` in the study harness; `src/rosa/` is untouched. The exact prompt lists of both arms and their SHA-256 are written to the run folder; each trace stores the prompt actually sent. Adoption is read from the traces (calls per request).
- Common: observation-only native guard (vendored from the baseline), read-only fixture, `accumulate_chat_history=False`, no retries replacing failed episodes.

## 3. Stage 1a
- Tasks: the six baseline tasks `t1 t2 t3 d1 d2 x1`, exact requests from `vendor/baseline_protocol.json` (hash recorded). Same fixture as the baseline: turtlesim `/diag_turtle/palette` (background 37/83/129) and demo talker/listener/add_two_ints under `/diag_demo`.
- Model: `qwen3.5:9b` at `http://172.30.80.1:11434`, temperature 0, seed 42, reasoning off, `num_predict` 1600, client timeout 90 s, ten executor iterations, 240 s per episode, as in the baseline, plus explicit `num_ctx` 65536 (the baseline did not set it; the active context is read from `/api/ps` before each stage and saved). The user's Ollama service is not restarted or reconfigured; only per-request options are sent.
- Design: 6 tasks × 2 arms × 2 repeats = **24 episodes**, one pass; within each repeat the 12 cells are shuffled with seed 20261112 so arms interleave. ROS domain 211, localhost only; snapshots before, every 6 episodes and after.
- Scoring (correctness first): vendored `baseline_audit.py` strict exact-field check against the oracle snapshot taken before the run (unchanged code); a trace-based **support screen** (every reported parameter value must equal a successful `ros2_param_get` result for that node; every reported type or name must appear verbatim in a tool result); every episode whose exact check and support screen disagree, and every failed episode, is read by hand and the verdict recorded with the trace line. Supported-complete = strict exact AND support screen pass (after manual adjudication).
- Metrics: supported-complete episodes per arm; model requests per episode, per supported-complete episode, excess over the Stage 0 strict floor (t1 4, t2 3, t3 3, d1 3, d2 4, x1 3); paired differences on matched (task, repeat) pairs where both arms are supported-complete, with the full list, mean, median, range and sign counts (no significance test at n ≤ 12); input/output tokens; native operations (`ros_start`); wall time; calls per request and multi-call requests.
- Reading rule: report the effect with its denominator and spread; do not extrapolate beyond these tasks; temperature 0 with one seed makes repeats near-duplicates, so repeats are not independent samples.

## 4. Stage 1b
- Fixture: N stock `demo_nodes_cpp talker` nodes, `-r __ns:=/scale -r __node:=nNN` with `-p use_sim_time:=<bool>`; N ∈ {4, 8, 16, 32}; value true when `index % 3 == 0` (index from 0), else false. Ground truth is that assignment, **checked before any run** by a direct `ros2 param get` read per node and a node-list inventory (both saved); runs abort if the oracle disagrees. Domain 212, localhost only, fixture torn down and verified empty after each N.
- Task text (fixed): "For every running node under /scale, report its configured use_sim_time. Return JSON with key clocks (an object mapping each full node name to a boolean)."
- Floor: `ros2_param_get` takes one node per call (checked in the schema), so the floor is discover → N parallel `param_get` calls → final answer = **3 requests** at every N. Native cost is not part of the floor.
- Arm A0 only. Models: `qwen3.5:9b` (same settings as 1a except `num_predict` 8192 so a 32-entry answer is not cut off, `max_iterations` 40 so serialisation shows as request count instead of an executor cap, episode timeout 900 s) and `gpt-6-luna` through the existing ChatGPT-plan OAuth path (`rosa-llm`, `parallel_tool_calls` true, no temperature or seed; model name and catalog entry recorded from the live catalog, explicit model required).
- Design: pilot at N=4 (1 episode per model, counts toward the cap), then N ∈ {4, 8, 16, 32} × 2 repeats per model. Order ascending in N per model. Caps: **16 Qwen, 16 strong episodes**, Stage 1 total ≤ 60 (planned 24 + 9 + 9 = 42). An episode lost to infrastructure failure (fixture died, Ollama or provider unreachable, oracle mismatch) may be replaced once under a new ID; the lost one is kept and counted. Model failures are never rerun.
- Truncation: any `done_reason: length`, provider length status, or iteration cap is recorded as a **capacity event** with its trace line.
- Metrics: coverage = nodes whose reported boolean equals the truth AND matches a successful `param_get` result for that node, out of N; requests, calls per request, whether `param_get` was issued in one request (parallel) or spread, tokens, native operations, wall time, retries, truncation events.

## 5. Stop and abort rules
Stop everything on: ChatGPT-plan access or throttling error (stop the strong-model part; the Qwen part may continue), Ollama unreachable, any fixture cleanup failure, a cap reached, or an oracle mismatch. Nothing is rescued by changing tasks, scorers or thresholds after seeing results. Documented protocol revisions are reported separately.

## 6. Decision rules (provisional, frozen now)
- **Ordinary prompt holds at scale:** at N=32 both models reach full coverage with requests ≤ floor+1 (≤ 4) in at least 80% of their N=32 episodes. With 2 repeats this means both episodes must pass. Conclusion would be that call count at scale is handled by the deconflicted prompt and the metric should change.
- **Gap at scale:** at N=32, requests ≥ 2× floor (≥ 6) or coverage < 100% on either model. Record the exact failure mode (serialisation, omitted nodes, output limit, loop) with trace lines. No mechanism proposal.
- **Inconclusive:** anything between, or fewer than 2 usable episodes in the N=32 cell of a model; say what extra runs would settle it.
- 1a: descriptive; the reading rule in section 3 applies.
- No claim of novelty, success or a selected algorithm.

## 8. Revisions after first inference
Pre-inference notes (not revisions): `score_stage1.py validate` re-scores the 36 original baseline episodes; the exact check reproduces the earlier independent `strict_correct` judgments 36/36 and, after fixing the screen's handling of endpoint roles (`publisher` is `Endpoint type: PUBLISHER` in tool output), the support screen agrees 36/36. Fixture smoke test (no model, N=32, domain 212): fixture became discoverable in 28 s; one of 32 oracle reads failed once with `Node not found` (transient discovery miss, 77 s for all reads). Clarification before any inference: the evaluation-only oracle may retry a failed read up to 3 times (all attempts saved); the agent's own reads never retry, and its failures are measured data.
Revisions after first inference (infrastructure only; no result had been scored or read):
1. **Run `stage1a_20261112T135750Z` aborted after episode 6** (`after-06` snapshot): one `ros2 node list` in the evaluation-only snapshot omitted `/diag_turtle/palette` although its direct `node info` read succeeded (the baseline closeout had the same discovery flake). The abort rule fired; all four fixture processes were stopped, the domain verified empty, the daemon stopped. The 6 completed episodes are kept (schedule indices 0-5) and will be scored with the rest.
2. **Resume instead of rerun:** the 24-episode cap forbids a second full run. A new run directory executes schedule indices 6-23 of the identical seeded schedule (asserted equal to the aborted run's `schedule.json`), with a fresh fixture started from the same commands, a new `before` snapshot (must equal the first run's `before` truth after canonicalisation), and the evaluation-only node enumeration retried up to 3 times. Model-facing code, prompts and settings are unchanged. Episodes 0-5 ran on fixture process set 1; 6-23 on set 2 (a restart between blocks is a documented difference).

3. **Run `stage1b_20261112T143327Z` stopped at N=32 before any N=32 episode** (readiness gate). It completed the N=4 pilot and N=4, 8, 16 for both models (18 episodes: 9 Qwen, 9 Luna). At N=32 `ros2 node list` showed 30 to 31 of 32 nodes in each of 8 attempts, and `/scale/n28` was never listed although its process was running and publishing (log kept). Cleanup was verified. This is a discovery-tool limit at width, not a model behaviour.
4. **N=32 cell as a separate continuation run** (new directory, `--only-n 32`, both models, 2 repeats each, no new pilot; caps remain 16 per provider, 9 used). Readiness: up to 8 listing attempts; if the listing is still incomplete the run proceeds **only if** the direct oracle read confirms all 32 nodes alive with the declared values (retry rule above); the readiness summary records the listing result. For each episode the scorer records which nodes ever appeared in a successful `node_list` result the agent received (`listed_by_agent`, `never_listed`), and reports coverage out of 32 AND coverage out of the nodes the agent was shown. Reading rule fixed now, before any N=32 episode: a coverage shortfall consisting only of `never_listed` nodes is labelled "discovery-tool omission", not "model omission"; the section 6 rules still apply to the headline coverage (/32) and the failure mode is named exactly.
5. **Scorer clarification after seeing 1b results (post-result, disclosed).** The first scoring pass required the key `clocks` and gave Qwen 0/32 at N=32. Reading the answers showed a complete flat `{"/scale/nXX": bool}` object without that key. The protocol defines coverage as nodes whose reported boolean equals the truth, so the scorer now reads a flat node-to-boolean object when `clocks` is absent, and records `format_ok` (requested key present) separately. Both numbers are reported; the headline decision uses value coverage and states the format deviation. Nothing else was changed, and the support requirement (a successful `param_get` result for the node) is unchanged.
