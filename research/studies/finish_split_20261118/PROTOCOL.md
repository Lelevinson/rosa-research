# Finish-tool split: frozen protocol

Dated 2026-11-18, Asia/Taipei. Written and hashed before the arm code, runner and freeze file exist. Development evidence only (synthetic fixtures, four small models); not a held-out result. Scorer v2.0 unchanged (SHA-256 `c6b02716152da0258b1296e7e6e0178d966c1c7c425f96e8c3f725bfd62b4ed9`). Held-out custodian files are not opened. Owner authorisation for this run: the owner's message of 2026-11-18 (finish-tool split run, smoke first, full run with nohup if the smoke is clean).

## 1. Question and why this is the smallest decision-changing run
The steady-loop ablation removed the finish tool **and** its prompt line together (arm NO_FINISH, 29/40 supported vs FULL 36/40, `steady_loop_ablation_20261117/REPORT.md`); Codex's blind audit found the 7 FULL-only cells were substantively wrong answers, not a format artifact (`AUDIT_UNBLINDED.md`). The tool and the prompt line are bundled, so the mechanism is unresolved. This study separates them. The ending-class recount (`candidate_counts_20261118`) shows text endings are rare in FULL arms (35 of 416) and are not obviously worse (82.9% vs 87.6% supported), so the ending class alone does not explain the -7. The result decides whether the finish tool stays in the method as a tool, as a prompt instruction, or as both (it changes what the method section says; it does not by itself add a new component).

## 2. Arms (each differs from FULL in exactly the stated way)
| arm | final_answer tool offered | prompt line about finishing | everything else |
|---|---|---|---|
| `FULL` | yes (C1: schema, one invalid-answer retry, ends the episode on acceptance) | yes: `FINAL_ANSWER_LINE` ("When you have the answer, call the final_answer tool with the answer as a JSON object, using exactly the keys the task asks for. Do not write the answer as plain text.") | pilot arm C1 unchanged |
| `TOOL_ONLY` | yes, same schema and description | **no finish line at all** (the base A1 prompt only) | as FULL |
| `LINE_JSON` | **no** | yes, new text, frozen here: `"When you have the answer, reply with the answer as a JSON object only, using exactly the keys the task asks for. Do not write anything else."` (system message, same position as `FINAL_ANSWER_LINE`) | as FULL; the episode ends on the first response without a tool call; scored by scorer v2.0 free-text extraction (last complete JSON object, unwrap), no retry |

Historical context, not re-run: ablation NO_FINISH (no tool, no line). Differences from the earlier arm that matter when comparing: LINE_JSON adds a format instruction that NO_FINISH did not have.

## 3. Design
10 development tasks (stage 3: `u3`, `p3`, `h4`, `v2`; e1h: `e1h_amb_1`, `e1h_amb_2`, `e1h_abs_1`, `e1h_abs_2`, `e1h_chg_1`, `e1h_chg_2`) x 4 models (`lfm3:1.7b`, `qwen3.5:9b`, `gpt-oss:20b`, `bonsai-2:4b`) x seeds 1 and 2 x 3 arms = **240 episodes**, 80 per arm. One fixture session per (model, environment) with all arms and both seeds of that session shuffled together (master seed 20261122). Settings as in every pilot-based study: temperature 0.7, think false, num_ctx 65536, num_predict 4096, 40 iterations, 90 s HTTP timeout, 900 s episode timeout, round-2 oracle with the 5 s retry (amendment 4). Models, digests, code and fixture hashes are recorded in `FREEZE.json` before the smoke. Runner: derived from `steady_loop_ablation_20261117/run_ablation.py`; arms in `split_arms.py`.
Known validity defect carried unchanged: the scripted-change hook in `e1h_chg_*` tasks misses when the model writes a node name without the leading slash, so the cell cannot be supported; such cells stay in the denominators.

## 4. Metrics, controls, and how the result will be read (frozen before the run)
- **Primary:** supported-complete cells (scorer v2.0) out of 80 per arm, and per model out of 20. Control: the fresh `FULL` arm of this run (concurrent, shuffled with the others). Historical FULL (36/40, 35/40, 32/40, 32/40 across four runs) is context only.
- **Paired view:** for each (task, model, seed) cell, FULL supported / other supported, counted as both, FULL only, other only, neither. Trajectories diverge from request 1-2 under any prompt change, so a paired cell is not a matched trajectory; the counts are descriptive, not a significance test.
- **Secondary (reported, no bar):** requests and input/output tokens per arm; ending class per arm (`final_answer` accepted, text answer, no answer: cap, backend error, timeout); finish-tool invalid-answer retries; episodes where the arm's finishing path was used differently from the arm's intention (for example a model calling `final_answer` in LINE_JSON is impossible because the tool is not offered: counted as `tool_not_offered` events); the earlier audit's question for the cells that differ (whether a differing answer is wrong in substance or in form) only if the cell count is large enough to hand-read, with Codex's blind-audit procedure if the owner wants it.
- **Reading rule.** Let `d_T = FULL - TOOL_ONLY` and `d_L = FULL - LINE_JSON` in supported cells of 80. "Close" means a gap of 3 or fewer, "separated" a gap of 6 or more. These thresholds are conventions taken from the earlier four-run range of 32-36 of 40 (about 10% of cells) and are not statistical tests; a gap of 4-5 is inconclusive.
  1. `d_T <= 3` and `d_L >= 6`: the tool is sufficient and the prompt-only route loses cells (reading: the tool carries the benefit in this setup).
  2. `d_L <= 3` and `d_T >= 6`: the instruction route is sufficient and the tool alone loses cells (reading: the prompt line carries it).
  3. both `<= 3`: either component suffices; the earlier -7 is not attributable to one of them (the bundle or a seed effect remains open).
  4. both `>= 6`: both parts are needed together (bundle).
  5. otherwise: inconclusive; report the numbers only.
  Each reading is limited to these 10 tasks, 4 models, 2 seeds and this fixture; it does not establish the mechanism by which the tool or the line helps, and it is not a held-out or causal claim. Per-model tables are reported because the weak models dominate the unsupported cells.
- No change to any prompt, schema, tool description or scorer rule after the run starts. A legitimate protocol revision would be reported separately.

## 5. Smoke, clean criteria and stop rules
**Smoke:** `qwen3.5:9b`, task `u3`, seed 1, three arms (3 episodes, not in any total), same runner. **Clean** means all of: (1) all three episodes finish with an `episode_end` and a trace, no worker crash, no oracle failure, no episode over 900 s; (2) arm fidelity read from the traces: FULL and TOOL_ONLY offer `final_answer` and LINE_JSON does not (`tools_offered` events); the FULL prompt contains the finish line, TOOL_ONLY's prompt does not mention `final_answer`, LINE_JSON's prompt contains the new line and no `final_answer` text; the three prompts differ only as in section 2 (checked by serialized-prompt comparison); (3) `collect` writes three rows with scorer v2.0 results; (4) Ollama loaded only the expected model and is unloaded afterwards (`keep_alive: 0`). An unsupported answer in a smoke episode is **not** by itself a stop condition (it is a model outcome); any harness, fixture, oracle or arm-fidelity anomaly is. On any anomaly: stop, report, do not start the full run.
**Full run:** one GPU/ROS job at a time (`curl http://172.30.80.1:11434/api/ps` and `pgrep -af "run_"` empty before start); start with `nohup`; stop and report if Ollama becomes unreachable, if three consecutive episodes fail for infrastructure reasons, or if another job takes the GPU. Infrastructure-failed cells (no model request made) are listed, excluded from the primary count and reported with and without them; none is silently dropped or re-run under a changed rule.
